# Kept remote sessions: survive a reload, move to another device (plan; step 1 built)

Status: **step 1 built (a reload on the same device gets its session back, see "Step 1: what was built" at the end)**, steps 2 to 4 not built. The text above "Step 1" is the plan as written; where it says step-up or reload grace, the owner's decisions at the end overrule it. (The owner's decisions of 2026-11-24 are at the end and overrule the proposals above them where they differ). Written 2026-11-24. Effort: **S** = hours, **M** = a day or two, **L** = several days. Nothing here is built; the code names below were read in the 0.28.0 tree, the measurements are not made yet (marked "to measure").

Reference: the MIT-licensed project MatGate (`real-ttx/Matgate`) has this feature. Every statement about it is marked **(read in its code)** or **(from a commit message)**. No code is copied; the ideas are small and the JulOS code already has most of the parts.

## What the owner wants

A remote desktop (RDP, VNC) that **is still there after a page reload, a killed phone app or a change of device**. When the same connection is opened and a session of it already runs, the page asks **"bring it here" or "start a new one"**. Reloading the page on the same device should not ask anything: it just goes back into the desktop.

It is security-relevant: a logged-in desktop is kept alive **without a browser**, and something must decide **who may take it**. The rule must be stricter than MatGate's.

## What exists today (0.28.0, read in the code)

- The server already keeps an RDP/VNC session when only the browser leg drops ([SESSIONS.md](SESSIONS.md), "Sitzungserhalt"): `ScreenRelay` in `JulOS.Integrations/Display/ScreenRelay.cs`. `Detach` parks the stream (`Park()`: encoding stopped, events drained), `ExpireAsync` ends it after `Keep`, every 10 s it asks whether the app session still lives (`WaitCheck`), `ResumeAsync` re-attaches (`Resume()`: key frame, new codecs).
- The only secret for re-attaching is a **random 192-bit token** sent to the page right after connecting (message 11) and **kept only in the page's memory** (`resume.js`). A reload, a killed phone app or a second device has no token, so the kept session is **orphaned until it expires**, and a new login on the target even takes the desktop over from it (xrdp and Windows give each user one desktop).
- `ResumeAsync` checks **owner = the app user** and the same answer for unknown and foreign tokens. It then **replaces `live.Alive`** with the check of the app session that resumed. So today the kept session is bound to the *last attached* app session; signing out another device does not end it.
- The keep time is **one value for the whole server** (`JULOS_STREAM_KEEP_SECONDS`, default 300, hard maximum 3600, `0` = off). Caps: per person `JULOS_MAX_SESSIONS_PER_USER` (8, `SessionRegistry`, a kept session keeps its lease), per engine 16 (`_slots`).
- The pop-out window already hands the token over through `window.opener` and never shows it in an address ([SESSIONS.md](SESSIONS.md), "Eigenes Fenster").
- SSH has no keep; work survives only with tmux on the target, and the browser re-attaches a tmux session after a drop ([CLI-SESSIONS.md](CLI-SESSIONS.md)).
- Step-up (fresh authenticator code or passkey, window 10 minutes by default) exists for actions ([SECURITY-REVIEW.md](SECURITY-REVIEW.md), F-04): `StepUpPolicy` (route based, `ApiGuard`), `SessionStore.GrantStepUpAsync`/`TakeStepUpAsync`, the sheet in `stepup.js`. A kept session is **not** covered by it today. The security history is `SecurityAuditStore` (`AddAsync(user, event, detail)`).

## How MatGate does it

- **Keep and re-attach** (read in its code, `Matgate/Display/ScreenSession.cs`): `Detach()` sets `_watched = false`, drops the viewer callback, switches sound off and sends a "release all keys" input to the backend; the connection stays. `Attach(viewer)` sets a new viewer, marks a re-open and a dirty screen (key frame), re-sends the cursor shape and pointer state. JulOS `Park()`/`Resume()` already do the equivalent.
- **Holder** (read in its code, `DisplayBridge.HeldScreen`): one viewer at a time, "the next one takes it" (`Take`), `Leave` keeps the screen for the user's keep time, `Watched` and `Since` are exposed. At most 16 held per user.
- **The list** (read in its code, `EndpointMapping.Display.cs`): `GET /api/display/{id}/open-sessions` returns the user's still running sessions **of that connection**: `{ session, watched, since }`. The caller needs the normal app sign-in (cookie authorisation) and access to the connection; a re-attach is then authorised by **that sign-in plus the session id, no further secret** (the session id is a random value the list hands out).
- **The question** (read in its code, `AgentScreenPage.cs`, and from the commit message of `20f88c9`): before connecting, the page asks the list. Its own previous session still running: take it. Otherwise, if exactly one other is running and **not watched** and the tab was restored: take it silently. Otherwise a notice with "bring here" and "new session"; a middle or Ctrl click asks for a second session on purpose. The commit message gives the reason: a second sign-in of the same Windows user throws the first out. (The commit `009b353` named in the task is **not in the shallow clone** I made, depth 50; I did not read it.)
- **Keep time** (read in its code, `MatgateUser.cs`): per user, one of `0, 5, 15, 30, 60, 120, 480, 1440` minutes (0 = off); a "restore everything" option forces at least 30 minutes (commit message of `20f88c9`: "sessions run at least 30 minutes"). Closing a tab ends its session at once (`/api/kept-sessions/end`, read in its code).
- **What it lacks, by my reading:** no second factor or step-up on a take; a stolen cookie can list and take every kept desktop; no device in the list; sign-out does not visibly end kept sessions (not checked in its code). JulOS can do better with parts it already has.

## The risk in one paragraph

Today a stolen cookie ([SECURITY-REVIEW.md](SECURITY-REVIEW.md) F-04) opens every connection with a **stored** password, but a connection whose password the person types each time (or whose desktop was logged in by hand, a locked-down account, a database console open) is closed to the thief. **A kept session removes exactly that barrier**: the desktop is logged in, no password needed. So taking a kept session must prove more than the cookie, whenever the cookie alone could be a thief's.

## Variants for "who may take it" (compared)

| | How | Stolen cookie | New device | Cost |
|---|---|---|---|---|
| **(a)** app session alone plus a server-side list (MatGate) | list + `session` id, no more | **Open**: the thief lists and takes every kept desktop, no code needed | open | S |
| **(b)** one-time **resume ticket** from an authenticated call, bound to the person, the kept session **and the app session**, valid ~20 s, single use | `POST` returns a ticket; the WebSocket takes only the ticket. The kept session's secret **never goes to a page** (also not in `sessionStorage`) | **Still open**: the thief has the same cookie, so the same app session, so the same ticket. Better hygiene (no long-lived token in the browser, ticket bound to one app session, audit entry), but not a barrier | open | M |
| **(c)** (b) **plus a fresh second factor (step-up)** when the taker is not "the same app session that was watching a moment ago" | see "Recommended rule" | **Closed in the case that matters**: a cookie alone cannot take a session that has been unwatched longer than a short grace, nor one from another app session | **Closed**: a new device is a new app session, so it always needs a fresh code or passkey | M |

**Recommended: (c).** It is (b) with one rule added, and the second factor is the one the project already has (the window of 10 minutes means one code covers several takes).

### Recommended rule (c)

A take is **free** only when all of these hold:

1. the app session asking is **the app session that last had the desktop attached** (`live.AppSessionId`, the id behind `SessionIdentity.Id`), and
2. the desktop has been unwatched for at most the **reload grace** (proposal: **2 minutes**), and
3. the connection is the person's own and the kept session belongs to them (owner check as today).

In every other case the take needs a **step-up approval** that is still valid (`TakeStepUpAsync`, or an approval inside the window from `GrantStepUpAsync`); without it the server answers `403 step_up_required` like for other guarded routes and the page opens the existing sheet and repeats once. This covers: another device (another app session), a phone coming back after hours, a long gap. If the switch "Require the second factor for actions" is **off**, the rule falls back to 1 to 3 alone plus "other app session = not free"; turning the switch off already warns that a stolen cookie reaches everything (F-04).

Why this shape: a reload (the common pain) is not interrupted, a thief with a copied cookie has to beat the grace window or the second factor, and **the second factor is never typed by me or stored** (rule 5 of [CLAUDE.md](../CLAUDE.md): the person enters it).

### The questions you listed, answered

- **A stolen cookie:** see above. It reaches only a desktop that was watched within the last 2 minutes by this very session (the thief would have to be faster than the person's reload). Everything else asks for a fresh code or passkey. A stolen cookie plus the second factor is out of scope (same class as F-04/F-33).
- **Two people on one JulOS:** the list and the take are filtered by `Owner = the person`; unknown and foreign ids answer the same (`ResumeFailed`, as today), so a person cannot tell whether an id exists. The list never shows another person's session, not even a count.
- **A kept desktop still logged in on the target:** this is the point of keeping, and the exposure window is the keep time. What we do: a **short default** (see Q1), a **hard maximum**, the take rule above, an easy **"End"** (account page, sign-in centre, device list), and a visible note while something is kept. What we do **not** do: lock the target for them (see "Not done").
- **The list as information:** only the person's own kept sessions, only after a sign-in, `Cache-Control: no-store`, **connection name** (the label the person gave, as in their own list), kind, since when, unwatched since when, a device label. **Never** host, address, user name on the target, password, token or the internal id of the engine.
- **Audit entries** (`SecurityAuditStore`, short codes, no secret; the user name of the person and `connection name · device label · minutes unwatched`): `kept.take` (only for takes from **another app session** or after a step-up, a plain reload is not written, to keep the 500-entry history readable), `kept.take_denied` (step-up missing or refused, wrong owner), `kept.end` (by the person, by a sign-out of that device, by "sign out everywhere", by a removed device). Parking and expiry go to the server log only.
- **Ending from the device list or the sign-in centre:** a kept session records the app session that last had it (`AppSessionId`). **Removing that device** from the device list ends the kept sessions it last had; **"sign out everywhere"** (`SessionStore.DeleteAllAsync`), a password change, a replaced authenticator and an account removal end **all** kept sessions of the person. This is **new** (today only the check of the last attaching session exists, see above) and is part of step 3. It hooks where the OIDC back-channel logout already hooks ([SIGN-IN.md](SIGN-IN.md), "Sign-out everywhere") so there is one place that says "a session of this person ended". Signing out on the device that has the desktop in the foreground keeps today's meaning: that desktop ends with it.

## What is kept, and for how long

**In scope: RDP and VNC (the stream engine).** The connection to the target and its state: the target's desktop, windows and logon stay. While nobody watches: **encoding stopped** (`Park`), sound off, browser events discarded (`Drain`), **keys released** (a gap in the middle of a held key would stick it on the target: the Park path must send "all keys up" like MatGate's `Detach`; to check whether it does today), nothing sent to the clipboard. On return: a **key frame**, the codecs of the new browser, the **pointer shape and position** (as `Resume()` does; to check that the pointer is re-sent).

**SSH terminals: not in the first steps.** Their work survives only with tmux on the target (programs started with the "program" session kinds, [CLI-SESSIONS.md](CLI-SESSIONS.md)); the browser already re-attaches after a drop. Keeping a plain SSH shell on the server means keeping a shell that may be in the middle of a command, `sudo` or a password prompt: that is a bigger risk than a desktop (a pager, a half-typed command), and a reload of a plain shell has an honest answer already ("the shell ends, tmux keeps"). Proposal Q3: only list **tmux program sessions** in the same list in a late step, behind the same rule; never a plain shell.

**Keep time: a setting per person**, valid for new sessions (a running one keeps what it was started with). Choices proposed: **off, 5 min, 15 min, 1 h, 4 h, 12 h**. **Default 15 minutes** (long enough for a phone that went to sleep and a lunch break, short enough that a forgotten desktop is not open all day). **Hard maximum 12 h**, set by the server (`JULOS_STREAM_KEEP_MAX_SECONDS`, replacing today's 3600 ceiling as the upper bound; the existing `JULOS_STREAM_KEEP_SECONDS` stays as the default for people who did not choose). I did not find a per-person settings store in a first look (`SettingsStore` looks instance-wide), so a small per-user column or table is part of step 2; to check before building.

**Caps:** the existing per-person cap (8, shared with watched sessions) and per-engine cap (16) already count kept sessions. Add a separate cap on **unwatched** sessions per person (proposal **4**) so that "forgot to close" cannot use all slots; the oldest unwatched is ended first when a fifth is parked, with an audit line `kept.end` "limit". Memory per kept session: framebuffer (a 1080p picture is about 8 MB as BGRA), decoder/encoder state of the engine, one reader task; **not measured, to measure** (the numbers decide whether 16 per engine stays).

**Server restart or update:** everything kept is **lost** (the connection to the target lives in the process). This is stated, not hidden: the release notes say so, the update note of [SELF-UPDATE.md](SELF-UPDATE.md) (when built) shows "N kept sessions will end", and after a restart the list is empty, the page just starts a new session (the target may still hold the old logon: that is the target's business, as today). A graceful shutdown closes them cleanly (`EndAsync`). No persistence to disk, ever (it would put a live logon into a dump).

## The flow in the page

1. **Before connecting** (in `RemoteSession`, before `POST /api/remote/ticket`): `GET /api/remote/kept?conn=<connection id>` returns the person's kept sessions of **that connection**: `[ { id, since, unwatchedSince | null, device, ownLastDevice, needsStepUp } ]`. `id` is a **random public handle** (128 bit, not the engine token), useless alone because the take needs the app session, the owner check and, by the rule, maybe a step-up.
2. **Decision** (pure logic in a new `kept.js`, tested; same style as `resume.js`):
   - none: as today (ticket, new session);
   - the page remembers a previous `sid`/handle for this connection (see below, a reload) and that one is kept and **unwatched**: take it silently;
   - exactly one, **unwatched**, and the window was restored by the workspace of this device: take it silently (MatGate: the same, read in its code);
   - otherwise a quiet notice (the style of the existing "taken by another session" message): "A session of **Server** has been open since 14:02 on **Pixel, Firefox**, nobody is watching it." with **Bring it here** and **New session**; if it is **watched** the text says so ("you are looking at it on **Desktop**"). *New session* ends the old one first (otherwise the target would give the new login the desktop and show the old one "taken"); a middle or Ctrl click on the tile still means "second session on purpose" and asks nothing (same as `extra: true` today).
3. **Take** = `POST /api/remote/kept/take { id, sid }` → a **ticket** bound to person, kept session, app session, **20 s, single use** (the existing `ScreenTickets` with a second kind; no new class) → WebSocket `?ticket=` as for a new session. If the rule needs a step-up the POST answers `403 step_up_required`; the sheet opens; the POST is repeated once. The page then shows the existing "connecting" state and the **first frame is a key frame**.
4. **What the other device sees** when its session is taken: the existing state `taken` (code 777, "Übernommen"), with a new text "Taken over by **Pixel, Firefox** at 14:07" and a button **Bring it back** (the same take, with the same rule). It does not reconnect by itself (as the sibling case today). A device that was **not** watching just finds the session gone from its list next time.
5. **Reload on the same device:** the page keeps `{ connection id → sid, handle }` in **`sessionStorage`** (per tab, survives a reload, gone with the tab; no secret: the handle opens nothing without the app session, and the take rule applies). After a reload it asks the list, finds its own handle unwatched, and takes it silently (within the grace window, no code). A closed tab (not a reload) cannot be told apart by the server; the session simply waits like any other.
6. **Remembered windows per device** ([MULTI-SCREEN.md](MULTI-SCREEN.md)): the workspace restores the windows; each remote window runs the decision above. A device that restores five windows must not show five dialogs: restored windows pass `restored: true`; silent takes as above, otherwise **one** dialog per window queued one after the other (proposal: the first asks, "Bring all" is **not** offered, each desktop is a separate decision).
7. **Pop-out window:** unchanged; it keeps the opener hand-over with the token (the token path stays for the **live** reconnect after a network drop; the new handle path is for coming back **without** a token). While a session is shown in a pop-out it is **watched**, so the main window's reload sees it as watched and asks.
8. **The phone** (the app was killed in the background, the person comes back): the cookie is still valid (the PWA keeps it), `sessionStorage` is gone, so the page has no own handle. It asks the list; exactly one unwatched session of the connection → "Continue where you left off?" as a **notice with a button**, not silent (without a remembered sid we cannot tell a returning phone from a second device). Unwatched for more than the grace → the step-up sheet (a passkey touch on the phone). This is also **"continue on the phone"** of [MULTI-SCREEN.md](MULTI-SCREEN.md) step 7: the same call, the list shows the desktop's session as watched, the phone takes it, the desktop shows "taken".

## Risks and what is deliberately not done

- **A kept desktop is a logged-in desktop without a person.** Limits: default 15 min, hard 12 h, step-up beyond a 2 min grace, cap on unwatched, End everywhere, short list text. It does not remove the risk of a forgotten desktop inside the keep time.
- **Not done: locking the target** when parking (e.g. sending Win+L) — it works only on some targets, needs keystrokes into a desktop nobody sees and would also lock a session the person wants to find open. Idea for [IDEAS.md](IDEAS.md) if wanted.
- **Not done: persistence across restarts**, sharing one session between two people, **two viewers at once** on one session (one viewer at a time, the next takes it, as MatGate's `Take`, read in its code), keeping SSH shells, a "kept for ever" mode, a push message for a waiting session.
- **Not done: removing the stateless token path.** The live reconnect after a short network drop keeps using the token from message 11 ([SESSIONS.md](SESSIONS.md)); it never leaves page memory and is not changed.
- **Race at a take:** two devices take at once. The existing `AttachLock` and "the next one takes it" already serialise; the loser shows "taken". Tests exist for the single-slot case; a two-taker test is part of step 3.
- **The grace window is a guess** (2 min). If it annoys on a slow phone reload, raise it; if a security reviewer dislikes it, set it to 0 (every take then asks, except a continuous reconnect).
- **A second login on the target** while the first is kept (a new session started with "New session") ends the kept one first; if the end fails the target would take over anyway: the page shows the existing "taken" text.

## Open questions for the owner (each with a proposal)

1. **Default keep time and maximum?** Proposal: default **15 min**, choices off/5 min/15 min/1 h/4 h/12 h, hard maximum **12 h**. (Today: 5 min and 1 h. MatGate: up to 24 h, read in its code.)

If the switch "second factor for actions" is off (or the person has no second factor), there is nothing to ask for: should a take from a new device then be **blocked** or **open** (as MatGate)? Proposal: **open**, with the existing warning of that switch.
3. **Is SSH in?** Proposal: **no for plain shells**; tmux program sessions later, step 5, behind the same rule.
4. **What does "watched elsewhere" do?** Proposal: **ask**, and say where ("you are looking at it on Desktop"); the take ends the other viewer with the visible "taken by <device>" and a "bring back" button. No silent takes of a watched session.
5. **One dialog or one per window when the device restores several?** Proposal: **one per window**, in order; silent for the single unwatched match.

7. **Per connection override?** Proposal: **not now**; one setting per person. Add "never keep this connection" only if a connection (a server console) needs it.

- **Default keep time: 15 minutes** (choices off, 5 min, 15 min, 1 h, 4 h, 12 h; hard maximum 12 h), as proposed in question 1.

## Step 1: what was built (2026-11-24)

A reload on the same device gets its remote session back, silently, without a second login on the target. Released with the version named in the CHANGELOG.

**Server** (`ScreenRelay.cs`, `ScreenTarget.cs` with `ScreenTickets`, `RemoteEndpoints.cs`, `KeptTakeRule.cs`, `DeviceLabel.cs`)
- A kept session gets a **public handle** (128 bit, random, never the engine token), remembers connection id and name, the device label (browser and system from the User-Agent, for display only), the app session that last had it and, while nobody watches, since when. The handle reaches the page in message 11 (after the token, separated by a space).
- `GET /api/remote/kept?conn=<id>`: the person's own kept sessions of that connection: `{ id, name, since, unwatchedSince?, device, own }` (`own` = this app session had it last). `Cache-Control: no-store`; never host, address, target user or token.
- `POST /api/remote/kept/take {id}` answers `{ ticket, layout, drive }`: a one-time ticket, **20 s**, bound to the person, the kept session **and the app session that asked** (`ScreenTickets.CreateKept` and `Redeem`: the second kind of ticket on the existing class). The WebSocket takes only the ticket (`?ticket=`); `ScreenRelay.RunAsync(takeHandle: ...)` re-attaches (the old resume path, so the same owner check, key frame and re-sent state). Unknown, expired and foreign handles answer exactly alike (404 "gone"). Rate limit 30 per minute and person.
- `POST /api/remote/kept/end {id}` ends one (204 whatever it was).
- **Who may take it:** the owner check (`ScreenRelay.FindKept` and the lookup in `RunAsync`: the handle resolves only for the owner), the app-session binding of the ticket (`ScreenTickets.Redeem`), and the one named place `KeptTakeRule.Allows`, which today returns true. **No step-up and no reload grace** (owner's decision of 2026-11-24); the comment there says where the optional second factor would go.
- **Ending:** signing out ends the kept sessions that app session last had, at once (`POST /api/auth/logout` calls `ScreenRelay.EndByAppSessionAsync`, audit `kept.end` with "sign-out"). The check every 10 s of a waiting session against its last app session already existed and covers the rest: "sign out everywhere" (the CLI `user logout`, `logout-others`), a removed device, a password change and a replaced authenticator all delete app sessions, so those kept sessions end within 10 s. **What step 3 still has to add** is the immediacy and an audit line for those paths; no extra hook was needed for correctness.
- **Audit** (`SecurityAuditStore`): `kept.take` only when the take comes from another app session than the one that last had the desktop (written when the ticket is issued), `kept.take_denied` (unknown or refused), `kept.end` (by the person, by sign-out); detail is `connection name · device · minutes unwatched`, never a handle or token.
- **While nobody watches** (`ScreenStream.Park`): encoding stopped, sound off, events discarded, and now **all pressed keys and mouse buttons released** (`ReleaseInput`; `Park` did *not* do this before, a held key would have stuck). Nothing is sent to the clipboard (events are drained). On return `Resume` sends a key frame, size, encoder, **pointer shape** and the sound state; the server keeps no pointer *position*, the browser sends its next move.
- Keep time stays the server-wide value (`JULOS_STREAM_KEEP_SECONDS`).

**Browser** (`kept.js`, `app.js`, `stream.js`)
- `kept.js` (pure, `tests/frontend/kept.test.mjs`): `decide` and `reclaim`. The page keeps `{connection id -> handle}` in `sessionStorage` (per tab, not a secret). `RemoteSession.start` asks the list **before** it asks for a new ticket, only on the first connect of a session, only when no other session of the same target is open in the page, not for Quick Connect. Its own handle unwatched: take, silently. Still "watched" (the old socket of the reload not yet noticed by the server): ask again up to four times, 0.5 s apart. Anything else (no remembered handle, gone, several, a copied tab): a new session as before. The dialog "bring here / new session" is step 3.
- **The page no longer ends the session when it is left.** `beforeunload` used to call `disconnect()`, which sends "end" (message 17); it now calls `leave()`, which only cuts the line. Without this a reload would have ended the desktop before the page could ask. "Close session" in the app and `disconnect()` still end it and forget the handle.

**Differences from the plan**
- No step-up, no grace window, `needsStepUp` is not in the list (owner's decision).
- The list also shows `name` (the connection's name, allowed by the plan) and `own`; the plan's `ownLastDevice` is called `own`.
- The ticket carries no device; the audit uses the asking request's User-Agent for the device label.
- The audit line `kept.take` is written when the ticket is issued, not when the WebSocket redeems it (the server side of the take has no database handle; the two are seconds apart; an unused ticket leaves a line).
- No `kept.` i18n keys: the silent take shows no text in step 1. The only new text is the server's "this session no longer exists", which the page never shows (it falls back to a new session) but the error-text table requires: `err.keptGone` (the `err.` prefix is what the i18n test checks for that table).
- The reload text of [SESSIONS.md](SESSIONS.md) changed accordingly.
