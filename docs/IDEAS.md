- 2026-11-19 **Stream engine: sharper text, faster on slow links, certificate fingerprint (branch `claude/scharf-tempo-c5719a`).** Test desktop 1024 x 640 (xrdp, XFCE) with a syntax-coloured GTK text view at 11 pt and 8 pt and a terminal with black-on-white, coloured and grey text; Guacamole is exact, so its canvas is the truth. Details of the code are in [ARCHITECTURE.md](ARCHITECTURE.md).
  - **Where the softness comes from (step 1).** Measured on the three text rectangles, stream after 5 s against Guacamole (mean absolute error 0..255 / share of pixels more than 32 off / worst pixel): editor 11 pt 2.43 / 1.97 % / 161, editor 8 pt 1.27 / 1.47 % / 167, terminal 2.93 / 4.77 % / 107. Split into planes, luma is off by 0.7 to 1.5 and chroma by 0.7 to 1.9 on average, but the damage is concentrated on edges of coloured strokes (blue keywords, orange names, red text): one-pixel strokes lose their colour in 4:2:0, and no quantiser fixes that (engine-tuning: minimum quantiser 12 instead of 22 changed coloured text by less than 5 %). Not the cause here: the first key frame (error is final after 3 to 5 pictures, 0.44 s from connect), the repeat convergence, the bit-rate bucket (a still screen is far below it), scaling (canvas 1:1 at dpr 1; the earlier 0.8 zoom is fixed on main), complexity or profile. **4:4:4 is out:** this browser reports `isConfigSupported` true for `avc1.f4001f` (High 4:4:4 Predictive) and for VP9 profile 1 and AV1 (software decoders), but libopenh264 encodes 4:2:0 only, there is no 4:4:4 encoder in the stack, and phone hardware decoders do not take High 4:4:4 (not tested on a phone).
  - **Decision: lossless refinement of settled tiles, not a new quantiser.** Tiles of 32 x 32 that stayed quiet for 120 ms are sent as palette PNG (at most 256 colours per rectangle, else the stream keeps them) and drawn over the video; changed tiles are cleared before the picture with the change goes out (messages 40 and 41). Result against Guacamole: all three rectangles exactly 0 error (worst pixel 0 in both editors, 6 in the terminal where the cursor sits), the whole screen except the wallpaper gradient 0.01 / max 5; converged 0.45 to 0.65 s after connect (the H.264 picture is final after 0.44 s, the PNGs follow within 0.2 s, 133 tiles, 86 KB next to 42 KB of video for the whole first screen). Checked with a window opened over the editors and closed again: no stale overlay either time (error 0 against a fresh Guacamole grab). Cost: no measurable server CPU (19 to 21 % of a core with and without, video load) and no change under motion (click median / p90 without refinement 45 / 86, 52 / 94 ms, with 44 / 68, 52 / 69 ms; load average 3 to 8 from other sessions). Photos and video are not refined (too many colours); there the quantiser still decides.
  - **Slow links (step 2).** The old behaviour on a 3 Mbit/s link with 30 ms each way (throttling proxy `deploy/dev/bench/slowproxy.py`) and a noisy video as load: click median 1.07 to 1.37 s, p90 1.08 to 1.67 s, 2.5 to 3 pictures a second, because three pictures sized for 16 Mbit/s queue in the socket. With `LinkPacer` (four runs of the final version, the first one with other sessions loading the machine to 14): median 0.72, 0.23, 0.20, 0.42 s (p90 0.87, 0.40, 0.56, 0.60 s), 5 to 14 pictures a second, bit rate settles near 2.4 Mbit/s; server CPU 14 to 27 % of a core against 12 to 21 % (it sends three to four times as many pictures). Fast link (100 Mbit/s, 60 ms round trip, quiet machine, moving video): median / p90 with the pacer 114 / 123 (2 of 20 clicks not seen within 4 s in that first run, 0 in the others) and 124 / 135 ms, without 92 / 123 and 120 / 131 ms: no difference beyond the noise of single runs. The first version of the pacer judged "delivery below the allowed bit rate" as congestion and wrongly throttled low-motion video on a fast link (the pictures were just small); the pacer now needs a full window with large pictures, and a simulated link with 300 ms round trip and small pictures is a unit test. **Not kept: 60 fps mode.** `FramesPerSecond` is only the pace the rate controller assumes, it caps no picture, and with a 60 Hz test source the stream delivered 26 pictures a second with the value 30 and with 60 (xrdp is the limit there); `JULOS_STREAM_FPS` was removed again. `bufferedAmount`: the browser cannot read the server's send buffer, so the pacer uses how long the socket needs to send a picture instead (60 ms counts as congestion), plus the acknowledgement round trip of small pictures. Not done: pooled buffers instead of `data.ToArray()`, input coalescing, a WAN test with real packet loss (the proxy has no loss), Android Chrome.

## Desktop modules without a backend yet: design notes (2026-11-19)

**Status 2026-11-19:** built (off by default, see [MODULES.md](MODULES.md)): service widgets with a Jularr template, Caddy read through the admin API (health, routes, certificates, configuration without secrets, access log), DDNS comparison plus an update stage with provider adapters and a history, and the "Heimnetz" card. Not built: Docker, Caddy writing (draft in MODULES.md). The questions below are still open; the built defaults are the safest answers.

The build plan for the Docker module and for Proxmox, Synology and Home Assistant integrations (one shared layer, levels, security model, milestones) is in [INTEGRATIONS.md](INTEGRATIONS.md); it supersedes the open Docker questions below.

The mockup has windows for Docker, Caddy and DDNS. Each one touches something with more power than the rest of JulOS (the Docker socket, the Caddy
admin API, a DNS token), so each gets the same shape. Apart from that, [SCOPE.md](SCOPE.md) still decides when any of this is started (milestone 3).

**The same rules for all three**

1. **Off by default, one switch per feature** in the server settings, for example `JULOS_DOCKER=off|read|control` (same for `CADDY`, `DDNS`). Off means the
   endpoints answer 404 and the tile says "nicht eingerichtet". `read` is the first version of each; writing is a second, separate step with its own switch value.
2. **Read-only first.** The first version of every module can only look: it ships, gets tested on the phone and the PC, and only then does anyone design the write path.
3. **Never hand the raw power to the browser.** The browser calls fixed endpoints with checked values (like `/api/agent/*` today); the server never forwards free-form
   requests or paths to Docker, Caddy or a DNS provider. Every endpoint needs a session, as everywhere.
4. **Secrets are stored like the connection passwords:** AES-256-GCM with `JULOS_SECRET_KEY` (`SecretBox`, the row id bound in as associated data), only the server
   decrypts, no API returns them (the list only says "gespeichert"), no log line contains them. Without a key the module cannot store a token and says so.
5. **Every change is logged** (who, what, when, result) in a small table and shown as "Verlauf" in the window; read calls are not logged.
6. **The server cannot lock you out of itself.** JulOS never edits the Caddy route or the container that serves JulOS (see below), and every write has a way back.
7. **Tests with fakes, not the real thing:** a fake Docker API and a fake Caddy admin API in the test project (like `FakeAgent`), a fake DNS provider. Real systems only by hand on the test instance.
8. A new container (the socket proxy, a Caddy filter) is a new service; [SCOPE.md](SCOPE.md) rule 4 asks to write down why it cannot be done without it. That reason is given in each entry.

**Docker (containers, state, CPU and RAM; later start, stop, restart)**

- *What is dangerous:* whoever can talk to `/var/run/docker.sock` is root on that machine (start a privileged container with `/` mounted). So the JulOS container never gets the socket.
- *Least risky design:* a socket proxy as its own small container in the compose file (for example `tecnativa/docker-socket-proxy`): it is the only container that mounts the socket, listens only in the internal compose network (no published port) and allows only the listed API sections, with `POST=0` (read only) in the first version: `CONTAINERS=1`, `INFO=1`, everything else 0. JulOS gets `JULOS_DOCKER_URL=http://docker-proxy:2375` and calls only `GET /containers/json` and `GET /containers/{id}/stats?stream=false`, reduces the answer to name, image, state, status, CPU and RAM and drops everything else (environment variables of other containers must never reach the browser).
- *Why a new service:* the alternative is mounting the socket into JulOS itself, which turns any bug in JulOS into root on the host. The proxy is 1 MB of HAProxy config and removes the dangerous half of the API from JulOS's reach. Weak spot that stays: with `CONTAINERS=1` the proxy also allows `GET /containers/{id}/json`, which contains environment variables (often passwords), so a JulOS compromise could read them; JulOS must not call it and the code review has to keep that so. A host-side script that prints only the needed fields to a Unix socket would close even that, at the price of a custom component to maintain.
- *Second step (switch value `control`):* start, stop and restart only (`POST=1`, `ALLOW_START=1`, `ALLOW_STOP=1`, `ALLOW_RESTARTS=1`), only for containers that carry a label such as `julos.control=true`, never for JulOS's own container, with a confirmation dialog and a log entry. No create, no exec, no delete, no image pulls. The mockup's "New Container" needs ports, volumes, environment and images: that is the whole attack surface of Docker, so it is explicitly not part of any early version.
- *Logs of a container* are useful but can contain secrets and are large: a separate decision, read-only, last N lines, opt-in per container.
- *Questions for you:* (1) Where does Docker run that you want to see: the machine that also runs JulOS, the VM, or another host? (2) Are you fine with one extra container (the socket proxy)? (3) Should JulOS only watch, or also start/stop/restart, and which containers? (4) Do you want CPU/RAM per container (costs one stats call per container every few seconds) or only the state? (5) Do you really need "New Container", or is the compose file the place for that? (6) Logs: yes or no?

**Caddy (domains and where they point; later add and remove)**

- *What is dangerous:* the Caddy admin API (default `localhost:2019`, no login) can replace the whole configuration: it can open any internal service to the internet or serve files from the host. Reaching it is as powerful as being root for everything Caddy touches. It is also how the way into JulOS is configured.
- *Least risky design, first version:* read the running configuration only. A second, tiny Caddy (or any small reverse proxy) sits in front of the admin socket and lets exactly one request through: `GET /config/apps/http/servers` (method matcher, one path). JulOS talks only to that filter, parses the routes into rows "domain, upstream" (the mockup's list), and shows the upstream address as text. The reachability dot per upstream can come later from a plain TCP connect check made by the server (no Caddy call). Why a second Caddy: the admin socket cannot be limited to reading by file permissions, so the limit has to be a component in between; the cheaper variant is to mount the Caddyfile read-only and parse it, which needs no new service but understands only simple files.
- *Second step:* add and remove "domain to upstream" routes through the admin API, but only objects JulOS created itself (JSON config objects carry an `@id`, for example `julos-<name>`; JulOS may only address ids with that prefix), never the route that serves JulOS. Before each change JulOS saves the current config; if the JulOS health URL does not answer within 30 s after the change, it puts the old one back. Upstream and domain are checked (allowed zone, no `localhost`, no metadata addresses). Starting a certificate request for a new name has side effects (rate limits), so the dialog says so.
- *Config and logs:* "Config" in the mockup is read-only text of the adapted JSON (secrets in a Caddy config, for example DNS challenge tokens, are removed before display). "Logs" only if Caddy writes an access log to a file or journald that JulOS may read; otherwise skip.
- *Questions for you:* (1) Does Caddy run in Docker or on the host, and is it the same Caddy that fronts JulOS? (2) Do you edit a Caddyfile by hand? Then API changes are lost on the next reload, or you stop hand-editing and let JulOS own the generated part: that is a decision about how you work. (3) Is the read-only list enough for the first version? (4) For writing: which zone(s) may JulOS create names in, and which upstream networks are allowed? (5) Do you want logs, and where are they?

**DDNS (provider, current IP, synced or not; later update)**

- *What is dangerous:* a provider token. It is a password for your DNS: with it, whoever gets it can point your names anywhere. Cloudflare tokens can be limited to one zone and permission ("Zone, DNS, Edit") and optionally to source IP addresses; use exactly that, never a global key.
- *Least risky design, first version, no token at all:* a settings list of host names to watch. JulOS finds the current public address (either by asking one outside address-lookup service, configurable, or by asking your router on the LAN, for example the FRITZ!Box `GetExternalIPAddress` call, which leaks nothing outward) and resolves each name with the normal resolver. Equal means "Synced", different means "Not synced", with the last time checked. That already fills the mockup's card (status, current IP, domains) and needs no secret.
- *Second step (switch value `control`):* the provider panel with a token stored as above. JulOS only ever changes the DNS records named in the settings (type A or AAAA, existing records, never create or delete), only when the address really changed, at most once per few minutes, and records old and new value in the history table. "Update now" is a button; an automatic update by a background worker is a third switch because it acts without anyone looking.
- *Provider list:* start with the one you use (the mockup shows Cloudflare); others (DuckDNS, a generic update URL) are separate small adapters behind one interface, added only when needed. If the router or another tool already updates DNS, JulOS stays at the read-only first version and just shows the state.
- *Questions for you:* (1) Which provider, and which names? (2) Public IPv4 only, or IPv6 too? (3) Public IP from an outside service or from the router (which router)? (4) Should JulOS ever change DNS, or only show whether it is in sync? (5) If it changes DNS: automatically or only on a button press? (6) Is it acceptable that anyone holding a valid JulOS session can trigger an update (limited to the listed records by the design above)?
- 2026-11-19 **Stream engine: stall found and fixed, sharpness on a PC, what was measured and what was not.**
  - Stall (the early version stopped for good, even a key frame request got no answer): two real causes, both found by reading the pacing and both covered by tests. (1) The browser acknowledged only pictures it drew. A picture it dropped (no decoder open yet), one lost when the decoder was reopened on a key frame, and everything inside a decoder that failed or stopped giving output were never acknowledged, so each leaked one place of the window of 3; after three such pictures the server sent nothing. (2) A key frame request on a screen that stands still and is already sharp matched no branch of the encode loop, so nothing was sent and a browser that had lost its decoder stayed blank until something on the screen moved. Fixes: acknowledgements carry the picture's sequence number and cover everything up to it (`PictureWindow`, unit tests for lost, repeated, late and too-large numbers), the browser acknowledges on every path (drop, reopen, decoder error) and reopens a decoder that holds pictures for more than a second, and a requested key frame is always encoded. The 2 s watchdog stays (test: no acknowledgements at all give at most 3 pictures, then a key frame). The integration test for (2) fails on the old loop and passes now. Not reproduced: a decoder that holds pictures back on its own (some hardware decoders wait for later pictures when the stream says nothing about picture reordering); the client watchdog covers it, a `bitstream_restriction` (`num_reorder_frames = 0`) in the SPS would remove the cause and is the next thing to try on real hardware (Android).
  - Sharpness. The main cause was not the codec: on a PC the page asked the VM for 0.8 times the window in device pixels and stretched it by CSS (a 1024 px window got an 816 px picture at scale 1.255), and the picture was also a few pixels narrower than the window (rounded down to a multiple of 4), so even at 1:1 it was resampled. That hits Guacamole as well, but text is where it shows. Now: on a wide screen with a mouse the default zoom is 1 (one VM pixel per screen pixel, the phone keeps 0.8), and the picture is placed at exactly 1 / devicePixelRatio when it is within 2 % of that. Seen at 1:1 in the browser, the same terminal text at 0.8 is visibly soft and at 1 is crisp.
  - Codec sharpness of the stream itself, measured against a screenshot of the VM (same pixels, terminal text, 1:1, converged): grey text on black mean error 1.0 of 255, worst pixel 8, edge strength 100 % of the original, converged after 3 pictures (about 0.5 s on a loaded machine). Guacamole is exact (error 0). Saturated colored text (red, green, blue, yellow, cyan on black) has a mean error of about 10 and a worst pixel of about 90: H.264 here is 4:2:0 and a one pixel wide colored stroke loses its colour sharpness, which no quantiser fixes (minimum quantiser 12 instead of 22 gave 9.9 against 10.35). Readable, but not pixel exact; only a 4:4:4 profile (no WebCodecs support) or a lossless layer for still screens would change it. Quantiser limits and the rate controller are unchanged: floor 22, ceiling 51, 16000 kbit/s, mosaic fallback only when even the coarsest quantiser does not fit.
  - Speed and efficiency. Alternating rounds on the Docker test desktop (480x270 30 fps video, 20 clicks per run, 3 runs per variant, old code against new), but the machine was at load 33-48 on 6 cores with swap in use the whole time, so none of this is a result: click latency median / p90 old 119 / 290, 91 / 345, 157 / 222 ms; new 163 / 264, 58 / 108, 194 / 314 ms; server CPU 37, 40, 29 % (old) and 42, 27, 34 % (new) of a core. Both lost up to 2 of 20 clicks under that load. The only safe reading: nothing got slower, and the numbers of the earlier quiet run (81 ms median, 16 % CPU) have not been repeated. Not tried because there was nothing to measure it with: pooled buffers instead of `data.ToArray()` (one copy of a few KB per picture), 2 against 3 pictures in flight, 60 fps, an adaptive window, input coalescing, `bufferedAmount`. A try with a lower minimum quantiser (12) changed colored text by less than 5 % and was dropped. Repeat on a quiet machine before touching any of them; `deploy/dev/bench` is enough, run each variant in its own server container behind the same database and read the CPU time from the container's `cpu.stat`.
  - Tools: `deploy/dev/test-display.sh` takes `JULOS_DEV_NETWORK=<project>_default` to run against your own compose project instead of `julos-dev`. Still open: Android Chrome, a WAN link, a real Windows host, a real xrdp VM, several rounds on a quiet machine.
