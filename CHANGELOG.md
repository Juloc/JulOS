# Changelog

Alle wichtigen Änderungen an JulOS. Das Format folgt [Keep a Changelog](https://keepachangelog.com/de/1.1.0/), die Versionen
[Semantic Versioning](https://semver.org/lang/de/). Solange die Hauptversion 0 ist, kann sich noch vieles ändern.
Wie eine Version veröffentlicht wird, steht in [docs/RELEASING.md](docs/RELEASING.md).

## [Unveröffentlicht]

### Sicherheit
- **Sicherheits-Audit** (Stand 0.13.1, [docs/SECURITY-REVIEW.md](docs/SECURITY-REVIEW.md) neu geschrieben): 23 Funde (keiner kritisch oder hoch), Lieferketten-Tabelle (Hash, NuGet, Basisimage, vendored JavaScript), Empfehlungen für das Internet-Ziel mit Aufwand, Ablauf bei gestohlener Sitzung, verlorenem Handy und gekapertem Host.
- **Test über jede Route** (`RouteSecurityTests`): alle registrierten Endpunkte werden aufgezählt und ohne Sitzung aufgerufen; alles außer einer ausdrücklichen Erlaubnisliste muss 401 liefern. Dazu: jede schreibende Route ohne Kopfzeile oder mit fremdem Origin = 403, WebSocket mit fremdem Origin abgelehnt, Sicherheits-Kopfzeilen überall.
- **Behoben:** Fenster-IDs aus der Liste eines Agenten werden geprüft (nur Zahlen, Server und Client): eine ID wie `../../auth/logout-others?` ließ den Browser beim Antippen eine andere Route aufrufen. Der **Root-Helfer** verlangt die Anfrage-Zeile innerhalb von 15 s (ein stummer Client konnte sonst einen der vier Plätze für immer belegen). Offene Desktop- und Terminal-Verbindungen bemerken eine Abmeldung nach höchstens 15 s statt 60 s.
- Beim Start warnt der Server im Log, solange `JULOS_TRUSTED_PROXIES` nicht gesetzt ist.
- Neu: `caddy/Caddyfile.internet.example` (Client-Zertifikat für Browser, Agenten kommen nur an ihre drei Wege; mit Caddy geprüft), `.github/dependabot.yml` (NuGet, Actions, Docker, Compose), `.github/workflows/supply-chain.yml` (wöchentlich auf bekannte Schwachstellen), GitHub-Aktionen auf Commit-SHAs festgelegt, Abschnitt „Updates and security“ in `docs/RELEASING.md`.

## [0.13.0] - 2026-11-19

### Neu
- **Host-Agent, Stufe 3: Aktionen, jede bestätigt, nie still** (Agent 0.6.0, [docs/HOST-AGENT.md](docs/HOST-AGENT.md), Abschnitt „Actions“): Updates installieren (ein Paket aus der Liste oder alle, mit Fortschritt und Neustart-Hinweis) und Paketlisten aktualisieren, Neustart und Ausschalten, systemd-Dienste auflisten, starten, stoppen und neu starten, Docker-Container starten, stoppen und neu starten, Image neu holen, Logs lesen (10 bis 200 Zeilen, nur auf Anforderung).
- **Zweistufige Bestätigung am Server**: `POST /api/hosts/{id}/actions/prepare` nennt genau Host, Aktion und Ziel und gibt eine kurzlebige (60 s), einmalige Bestätigung zurück (nur ihr SHA-256 im Speicher, gebunden an Sitzung, Host, Aktion und Ziel); erst `…/actions/run` führt aus und prüft alles noch einmal. Bei Neustart, Ausschalten und „alle Updates“ muss der Rechnername getippt werden. Nie durch einen Zeitplan, nie durch den Agenten.
- **Zwei Schlüssel plus Pausenschalter**: der Server prüft die Stufe je Host (`agents.control`, Standard `read` = keine Aktion; neu einstellbar im Dialog „Host-Details“ → Aktionen: aus, Updates und Logs, alles), die Sitzung, ein Limit (30 Anfragen je Minute) und den Pausenschalter (`JULOS_HOST_ACTIONS=off` oder „Alle Aktionen pausieren“); der Agent prüft sein lokales Wort je Aktionsart in `/etc/julos-agent/permissions` (`updates`, `reboot`, `services`, `docker`, `logs`; nach der Installation keins gesetzt). Fehlt einer: abgelehnt.
- **Installer**: `--allow WORTE` setzt die Wörter bewusst (nie Standard); nur wenn etwas root braucht, wird der **Root-Helfer** `tools/julos-agent-helper.py` als socket-aktivierter systemd-Dienst installiert (der Agent selbst bleibt ein Benutzer ohne sudo und mit `NoNewPrivileges`; der Helfer führt je Anfrage genau ein festes Programm ohne Shell aus und prüft dieselbe Datei noch einmal). Das sudo-Passwort tippt man weiter selbst.
- **Verlauf (Audit)**: Migration 018, Tabelle `host_audit`: jede Anfrage, Ablehnung (mit Grund) und jedes Ergebnis mit Benutzer, Host, Aktion, Ziel und Zeit, ohne Geheimnis und ohne Ausgabe-Inhalt; `GET /api/hosts/{id}/audit` und die Ansicht „Verlauf“ im Dialog. Ohne Eintrag im Verlauf wird nichts ausgeführt.
- **Fortschritt und Rückweg**: lange Aktionen melden `progress`-Nachrichten; ein Verbindungsabbruch bricht nichts ab, der Agent merkt sich die letzten 20 Ergebnisse (`GET /v1/host/jobs`) und der Server holt sie nach der Rückkehr ab; ein Neustart wird zuerst „angenommen“ gemeldet. Pro Host läuft nur eine schreibende Aktion (409 busy).
- Oberfläche (Handy und Desktop): Tasten an Updates, Paketen, Diensten, Containern und im System-Abschnitt, Bestätigungsdialog mit Host, Aktion, Ziel, Warnungen (JulOS-eigene Container-Gruppe, zurückgehaltene Pakete), Fortschrittsbalken, Ergebnis mit Neustart-Hinweis; Texte Deutsch und Englisch. Service Worker `pd-v58`.
- Tests: `tests/agent/test_actions.py` (Request-Recorder für jede Aktion, Ablehnung je fehlendem Schlüssel, Injektionsfälle, Helfer mit einsetzbarem Runner, Agent gegen den echten Helfer-Code über einen Unix-Socket), `HostActionTests.cs` (Bestätigung: abgelaufen, wiederverwendet, falsche Sitzung, falscher Host, geänderte Aktion oder Ziel; Rate-Limit, Pause, Verlauf, Eigentum, Rückweg), `hostactions.test.mjs`.

### Grenzen
- Updates und Paketlisten nur mit apt; „Image neu holen“ holt nur das Image (neu erstellen muss man den Container selbst); Docker-Aktionen brauchen Zugriff auf den Docker-Socket mit Schreibrecht (ein reiner Lese-Proxy reicht nicht).
- Echtes systemd, echtes apt und echtes Docker auf einem echten Host sind nicht automatisch geprüft (Tests mit Recordern und Fakes).

- Tests: DES gegen veröffentlichte Vektoren und OpenSSL, jede Kodierung mit handgebauten Rechtecken, der Client gegen einen Testserver (Versionen, Anmeldung, VeNCrypt mit echtem TLS, Bilder, Zeiger, Größe, Zwischenablage, Eingabe) und `deploy/dev/test-vnc.sh` gegen zwei echte TigerVNC-Wegwerfziele in Docker (eigenes Netz, am Ende entfernt).

### Behoben
- Zwischenablage, Text vom Browser in die VM: der Text ging mit CR LF an xrdp, das ihn unverändert weitergibt; in der VM bekam jede Zeile ein CR (`^M` im Terminal, Fehler in Skripten). Jetzt geht LF hinaus; CR LF erst, wenn die VM selbst Text mit CR LF schickt (Windows-Rechner). `JULOS_CLIP_EOL=auto|lf|crlf` stellt es fest ein. Gegen ein echtes xrdp reproduziert und per Display-Test abgesichert.
- Zwischenablage, Text aus der VM zum Browser: der Echo-Filter verwarf Text, der dem zuletzt eingefügten glich, bis zum Ende der Sitzung (derselbe Text in der VM erneut kopiert kam nie an, „manchmal geht es“). Er gilt jetzt nur 1,5 s nach dem Einfügen und nur, solange die VM nichts anderes kopiert hat.
- Zwischenablage: eine Datenanfrage, die die VM nie beantwortet, blockierte alle späteren Kopien dieser Sitzung. Nach 15 s gilt sie als verweigert und die nächste geht hinaus.
- Fehler der Zwischenablage werden nicht mehr verschluckt: zu langer Text (über 1 MiB), keine Verbindung, Strg+V ohne Text im Browser, vom Browser verweigertes Ablegen (HTTPS, Fokus, Berechtigung) und ein fehlender Kanal der VM (`xrdp-chansrv`) erscheinen als Meldung; die Meldung „Text aus der VM kopiert“ ist antippbar und öffnet den Dialog. Text, der ohne Fokus der Seite ankam, wird beim nächsten Fokus noch einmal abgelegt. Strg+V wird auch bei Tastaturbelegungen erkannt, in denen die Taste nicht „v“ meldet.

### Neu
- Berechtigung des Browsers für die Zwischenablage sichtbar behandelt (`clipperm.js`): Zustand von `clipboard-read` und `clipboard-write` wird abgefragt (Firefox und Safari ohne `clipboard-read`: „unbekannt“), Lesen nur aus einer Geste (neuer Knopf „Aus der Zwischenablage holen“ im Dialog und neue Taste „Text einfügen“ in der Tastenleiste), vor der Abfrage des Browsers ein Hinweis, bei „verweigert“ der Weg zur Freigabe je Browser (Chrome/Edge, Firefox, Safari/iOS, Android), Rückfall Strg+V im Feld; ohne HTTPS sagt die Seite warum und kopiert aus der VM über ein verstecktes Textfeld (`execCommand('copy')`). Die Diagnose zeigt Kontext und Berechtigungen. Texte in Deutsch und Englisch.
- Zwischenablage-Diagnose im Dialog „Text senden“ („Diagnose“): Kanal der VM bereit oder fehlt, letzte Richtung und Zeit, ob die VM den Text abgeholt hat, letzter Fehler im Klartext, nie ein Inhalt. Neue Protokollnachricht 15 (Ereignis der Text-Zwischenablage). Im Server-Log steht je Ereignis eine Debug-Zeile (`Zwischenablage: <Art> (<Länge>)`, nie der Text).
- Doku: [docs/CLIPBOARD.md](docs/CLIPBOARD.md) beschreibt den Textweg und hat den Abschnitt „Fehlersuche“ mit Ursachen und Prüfbefehlen. Tests: echte Text-Tests gegen xrdp (`ClipboardRealTextTests`, mit dem Hilfsdienst `clip-probe.py` im Test-Desktop), Kanal- und Brückentests, `clipdiag.test.mjs` und ein Browser-Ablauf (Strg+C und Umschalt+Pfeile in einem echten Fenster der VM, Strg+V, Diagnose). - Tägliches Backup: der Server schreibt die Datenbank (komprimiert) und eine Kopie des Schlüssels für gespeicherte Passwörter als getrennte Dateien in einen Backup-Ordner (`/backup`, im Compose-Beispiel `~/julos-backup`), mit Aufbewahrung (Standard 14 Tage), Uhrzeit und Schalter per Umgebungsvariable (`JULOS_BACKUP`, `JULOS_BACKUP_TIME`, `JULOS_BACKUP_KEEP_DAYS`, `JULOS_BACKUP_KEY`). - Wiederherstellung auf der Konsole: `dotnet JulOS.dll backup restore DATEI --key SCHLÜSSELDATEI` (alles oder nichts, prüft am Ende, dass sich gespeicherte Passwörter entschlüsseln lassen); `backup create` sichert sofort. „Über JulOS“ zeigt das letzte Backup mit Zeit und Größe. Anleitung: [docs/BACKUP.md](docs/BACKUP.md).
- Module Caddy und DDNS, erste Stufe, nur lesend und standardmäßig aus (`JULOS_CADDY`, `JULOS_DDNS`, siehe [docs/MODULES.md](docs/MODULES.md)): Caddy zeigt „Domain → Ziel“ aus einem nur lesend eingebundenen Caddyfile und/oder der Admin-API (ein fester Abruf), mit einer Erreichbarkeitsprüfung nur der gelisteten Ziele; DDNS vergleicht die öffentliche Adresse (Router oder Lookup-Dienst) mit der Namensauflösung der eingestellten Namen („Synchron“ oder „Nicht synchron“, mit Zeit der Prüfung), ohne Token und ohne zu schreiben. Fenster im Desktop (Dock, Launcher, Menü) und Karten in der Handy-Shell erscheinen nur, wenn der Server das Modul eingeschaltet hat.
- Stream-Engine, wahlweise und standardmäßig aus (`JULOS_RDP_GFX=on`): das H.264, das ein RDP-Server durch die Grafik-Pipeline (RDPGFX) schickt, geht ohne neue Kodierung an den Browser (weniger CPU, eine Kodierstufe weniger). Liefert der Server kein passendes H.264, bricht etwas ab oder braucht der Browser ein Schlüsselbild, verbindet dieselbe Sitzung ohne Pipeline neu und kodiert wie bisher selbst. Das xrdp von Debian 13 liefert so kein H.264, Windows-Server (komprimierte Nachrichten) sind nicht unterstützt und nicht geprüft; Einzelheiten in [docs/RDPGFX.md](docs/RDPGFX.md). Gegen einen Server, der H.264 sendet, noch nicht erprobt.
- Stream-Engine: Sitzungserhalt. Bricht die Verbindung zum Browser ab (Handy wechselt das Netz, Tab im Hintergrund), bleibt die RDP-Sitzung auf dem Server `JULOS_STREAM_KEEP_SECONDS` Sekunden (Standard 300, 0 = aus) erhalten; der Browser nimmt sie mit einem Sitzungs-Token wieder auf, ohne neuen Login am Ziel und mit sofortigem Schlüsselbild, und zeigt „Verbindung wird wiederhergestellt …“ statt eines Abbruchs. Schließen in der App, Abmelden, Ablösen und Ablauf beenden die Sitzung wirklich.
- Stream-Engine: Laufwerksumleitung (RDPDR). Ein Ordner des Servers (Einstellung `JULOS_DRIVE_ROOT`, aus, wenn leer) kann je Verbindung als Laufwerk in den Desktop gereicht werden; im Verbindungsdialog zwei Schalter, beide aus: „freigeben“ und „Schreiben erlauben“ (ohne den zweiten nur Lesen). Streng abgesichert: fester Wurzelpfad nur aus der Server-Einstellung, nur Windows-Pfade unterhalb der Wurzel, kein `..`, keine versteckten Namen, keine Symlinks, keine Unicode-Tricks, `openat2` mit `RESOLVE_BENEATH`. Siehe [docs/DRIVES.md](docs/DRIVES.md). Auf einem echten Windows-Ziel noch nicht erprobt.

### Geändert
- Der Agent gehört jetzt zum Host statt zu einer einzelnen Verbindung und bedient alle Verbindungen seines Hosts. Die Wege dafür sind `/api/hosts/{id}/agent/code` und `/api/hosts/{id}/agent`; `/api/agents` und `/api/connections/{id}/agent/*` entfallen. Aufrufe des Agenten nehmen weiter `?c=<Verbindung>` oder neu `?h=<Host>`.
- Migration 008: bestehende Verbindungen kommen auf einen Standard-Host „Mein Rechner“ pro Benutzer, bestehende Agenten behalten ihr Token (hatte ein Benutzer mehrere, bekommt jeder weitere einen eigenen Host mit dem Namen seiner Verbindung). Offene Einrichtungscodes (10 Minuten) entfallen.
- Der Agent meldet Rechnername und Betriebssystem (nur zur Anzeige); ältere Agenten funktionieren unverändert.
- Entwicklung: `deploy/dev/e2e.sh` startet einen eigenen Test-Stack und prüft in einem echten Browser (Playwright in Docker, Chromium) sechs Abläufe: Ersteinrichtung und Anmeldung, Verbindungen anlegen, RDP-Stream mit Bild, Klick und Tastatur im Ziel, SSH-Terminal, Handy- und Desktop-Oberfläche ohne Konsolenfehler. Beschreibung in [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md), optionaler Schritt vor dem Tag in [docs/RELEASING.md](docs/RELEASING.md).

### Behoben
- Mikrofon: Die Kopfzeile `Permissions-Policy` sperrte das Mikrofon für die Seite (`microphone=()`); sie erlaubt es jetzt für die eigene Seite (`microphone=(self)`), alle anderen Rechte bleiben gesperrt.
- Stream-Engine: Der Ton wird dem RDP-Server jetzt als gewünscht gemeldet. Zuvor ging die Option „kein Ton“ an den Server, was auf Windows-Zielen den Ton verhindern kann (xrdp ignorierte sie).

### Entfernt
- Guacamole entfernt, die Strom-Engine ist der einzige Weg für Desktop-Verbindungen (eigener RDP-Client auf dem Server, H.264 im Browser mit WebCodecs). Weg sind der Relay und das Protokoll für guacd, der JavaScript-Client, die Wahl „Bildübertragung“ im Verbindungsdialog und in den Einstellungen sowie der automatische Rückfall; kann der Browser kein H.264 oder kommt keine Verbindung zustande, zeigt die Sitzung eine klare Meldung mit „Neu verbinden“. Wer einen Desktop aufmacht, ohne dass der Server den Kodierer (libopenh264) laden kann, bekommt die Meldung, dass die Bildübertragung nicht verfügbar ist.
- Für Betreiber: Der `guacd`-Container und alle `JULOS_GUACD*`-Einstellungen werden nicht mehr gebraucht und können aus der Compose-Datei (und aus `.env`) entfernt werden; wer die mitgelieferten Compose-Dateien nutzt, bekommt sie schon ohne guacd. Gespeicherte Verbindungen bleiben unverändert: alte Einträge mit der Engine „guac“ nutzen jetzt ebenfalls den Strom, die Spalte `engine` der Datenbank bleibt als Rest bestehen, wird nicht mehr gelesen und es gibt keine Migration. Das Laufwerk (`JULOS_DRIVE_ROOT`) steht jetzt jeder Desktop-Verbindung offen, die es einschaltet; die Felder `engine` in der Verbindungs-API und im Ticket-Aufruf entfallen (alte Clients dürfen sie weiter mitschicken, sie werden ignoriert).
- Die Hilfswege für Guacamole in der App (Foto über den Helfer, „Bild aus der VM holen“) sind weg, Bilder und Dateien gehen über den Strom; die Agent-Schnittstellen `/api/upload`, `/api/upload-file` und `/api/clipboard/pull` bleiben bestehen.


## [0.4.0] - 2026-11-19

### Neu
- Stream-Engine: Vertrauen bei erster Nutzung für das RDP-Zertifikat statt „Zertifikat ignorieren“: der Fingerabdruck wird je Verbindung gemerkt; ändert er sich, kommt vor dem Senden des Passworts eine Warnung mit altem und neuem Fingerabdruck (Abbrechen oder bestätigen). Guacamole verhält sich wie bisher.
- Stream-Engine: auf langsamer Leitung (WLAN, Mobilfunk, WAN) passt sich die Bitrate an die gemessene Liefergeschwindigkeit an und das Fenster der unbestätigten Bilder wird kleiner; Klicks reagieren dort nach etwa 0,3 s statt nach über 1 s.
- Stream-Engine: ruhende Bildteile (Text, Farbe) werden zusätzlich verlustfrei nachgeliefert und liegen pixelgenau über dem Video, farbiger Text ist damit so scharf wie bei Guacamole.

## [0.3.0] - 2026-11-19

### Neu
- Ton aus der VM im Browser und Mikrofon zur VM (Bildstrom-Engine): Ton nur von der gerade aktiven Sitzung, Mikrofon nur auf Knopfdruck mit Browser-Berechtigung und deutlicher Anzeige, höchstens eine Sitzung nimmt auf.
- Der Agent meldet sich von der Ziel-Maschine aus beim Server (WebSocket über HTTPS, ausgehend): Fensterleiste, Programmstart sowie Foto-, Datei- und Zwischenablage-Übertragung gehen jetzt auch, wenn der Server auf einem anderen Rechner läuft (zum Beispiel auf Cubi).

Der Agent bleibt eine einzige Python-Datei ohne Zusatzpakete; der Unix-Socket-Weg für denselben Rechner funktioniert weiter.
- Der Bildstrom kann auf einer Grafikkarte kodiert werden (VAAPI, zum Beispiel Intel QuickSync), wenn der Container `/dev/dri` sieht; sonst und bei jedem Fehler kodiert wie bisher die CPU (H.264). Dazu ein optionaler H.265-Strom, wenn Browser und Grafikkarte ihn können (`JULOS_ENCODER`, `JULOS_CODEC`); Prüfung mit `dotnet JulOS.dll diag encoders`, Anleitung in [docs/ENCODERS.md](docs/ENCODERS.md). Auf einer echten Grafikkarte noch nicht erprobt.
- Sicherheits-Review mit Bericht in [docs/SECURITY-REVIEW.md](docs/SECURITY-REVIEW.md).

### Geändert
- Die Aufrufe der App an Agent, Foto-Upload, Datei-Upload und „Bild aus der VM holen“ nennen die Verbindung (`?c=`); ohne Angabe gilt wie bisher der lokale Socket.

### Sicherheit
- Anmeldesperre auch für IPv6 pro Netz, Obergrenze für gleichzeitige Anmeldeversuche, begrenzte Größe von API-Anfragen, Grenzen für Uploads und die Dateisuche, Kontingent für Dateien, sichere Downloads (keine Named Pipes), Warnung beim Start ohne Schlüssel für gespeicherte Passwörter.

## [0.2.0] - 2026-11-19

### Neu

## [0.1.0] - 2026-11-19

### Neu
