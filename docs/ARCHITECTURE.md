# Architecture

Decisions for the server rewrite. The **basic structure stays the one used in the other projects** (solution layout, the split into
host, backend library, integrations, workers and tests, the folders around them). Optimising happens *inside* that structure, never by removing it.

## Principles

1. **Keep the skeleton.** Same solution layout and folder names as the sibling projects, so every project reads the same.
2. **Write it ourselves where that is reasonable.** Full control, small attack surface, speed. A dependency has to earn its place.
3. **Do not hand-roll cryptography or the database driver.** Mistakes there are invisible. Those use the framework or one small, well known library.
4. **Fast by default:** minimal APIs, JSON source generation (no reflection), pooled buffers in the relay, one shared database data source, ReadyToRun, a trimmed non-root runtime image.

## Stack

| Part | Choice |
| --- | --- |
| Server | C# on .NET 10, ASP.NET Core host |
| Browser | Plain ES modules, WebCodecs for the desktop picture (`stream.js`) and xterm.js for terminals, served as static files (the PWA) |
| Database | PostgreSQL, plain SQL through Npgsql, SQL migrations in `database/`, no ORM |
| Remote display | The server's own display engine: RDP client, H.264 encoder (libopenh264, optionally VAAPI), WebSocket to the browser (see "Display engine") |
| Terminal | SSH client in the server (SSH.NET behind `ISshSession`), text to the browser, drawn there by xterm.js (see "Native terminal") |
| Linux agent | Python (GTK/Wnck, standard library only apart from PyGObject) behind the language-neutral agent API; it connects outbound to the server (WebSocket) or, on the same machine, answers on a Unix socket; a Windows agent later in C# |
| Delivery | One image on ghcr.io (amd64, arm64) and a compose file |

## Layout (same shape as the sibling projects)

```
JulOS.slnx  global.json  Directory.Build.props  Directory.Packages.props  .editorconfig
src/
  JulOS.Frontend/       ASP.NET host: static client (PWA), HTTP API, WebSocket endpoint, security headers
  JulOS.Backend/        class library: Services, Logic, Data (PostgreSQL access), accounts, sessions, connections
  JulOS.Integrations/   outside communication: the display engine (RDP client, H.264) with its relay and one-time tickets, the SSH relay, the agent client (Unix socket), the agent link registry (outbound WebSocket of the agents)
  JulOS.Workers/        background jobs: purge expired sessions and tickets, upload clean-up
tests/
  JulOS.Backend.Tests/  unit and integration tests (including a real SSH target and PostgreSQL in containers)
database/               numbered SQL migrations
deploy/                 compose files, Caddy examples
docs/                   vision, scope, ideas, architecture, agent API
tools/                  Linux agent, installers, user tool
```

Inside a project, code is grouped by feature (Auth, Remote, Files) and, in the backend, by Services / Logic / Data as in the siblings.

## Written ourselves

The screen relay and the RDP client with the H.264 pipeline, the SSH relay (WebSocket protocol, host key policy), one-time connection tickets, sessions with rotating cookies, TOTP (RFC 6238) and recovery codes,
login lockout, the migration runner, the SQL access helpers, security headers and the CSRF/origin checks, the agent client, the upload path.

## Not written ourselves, and why

| What | Use | Why |
| --- | --- | --- |
| HTTP/TLS server | Kestrel (part of the framework) | Mature and fast |
| PostgreSQL wire protocol | Npgsql | A driver is not worth hand-writing |
| Cryptographic primitives (HMAC, AES, random) | .NET base library | No hand-rolled crypto |
| Password hash | Argon2id from one small library (Konscious), hash format versioned | Memory-hard hash is the one place where a custom version would be risky |
| SSH client | SSH.NET (MIT) behind our `ISshSession` | A full SSH client (key exchange, ciphers, channels) is large and a crypto building block; the interface keeps it replaceable and the relay testable without a network |
| Passkeys (WebAuthn) | Fido2 4.x (MIT) behind our `IPasskeys`; it brings NSec (libsodium, native), `System.Formats.Cbor` and `Fido2.Models` | Verifying attestation and assertions (CBOR, COSE keys, flags, signatures, counters) is protocol and crypto work that must not be hand-written; one file (`Fido2Passkeys.cs`) knows the library, see [PASSKEYS.md](PASSKEYS.md) |
| Terminal emulator in the browser | xterm.js (MIT, vendored in `wwwroot/lib/xterm`, no CDN) | Terminal emulation (escape sequences, unicode widths, selection, scrollback, renderers) is years of work; we write the session, key mapping, touch handling and host key dialog around it |

Target for runtime NuGet packages: **four** (Npgsql, the Argon2 library, SSH.NET and Fido2 with its parts NSec/libsodium, CBOR and Fido2.Models). Test packages are separate. Versions are centralised in `Directory.Packages.props`.

## Security model

- **Account:** Argon2id for the password, TOTP as second factor, ten one-time recovery codes. Passkeys (WebAuthn) later, see `IDEAS.md`.
- **Session:** 256-bit random value in a cookie (`__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Strict`), stored only as SHA-256 in PostgreSQL. Idle timeout 30 days, absolute 180 days, rotated every 12 hours with a short grace for parallel requests. Survives server and browser restarts.
- **Lockout:** per address and per account with growing delay. An address is the IPv4 address or, for IPv6, the whole /64 prefix (one connection can rotate through its /64). At most three password checks per address run at the same time (Argon2 needs 64 MiB each), so a burst of parallel requests cannot get past the counter or fill the memory.
- **Every API and the WebSocket need a session.** State-changing requests also need a custom header and a matching `Origin`. Static files and the manifest are public so the app can be installed.
- **Connection ticket instead of an encrypted token:** the browser asks for a one-time ticket (random 128 bit, 30 s, kept in memory with the connection settings) and opens the WebSocket with it. The ticket only works for the user who asked for it, and the WebSocket also checks the `Origin`.
- **Target passwords:** by default the password is typed per connection, held in memory for at most 30 s, never logged or stored. On request a connection can keep its password: it is encrypted with AES-256-GCM (key `JULOS_SECRET_KEY`, 32 random bytes, only in the server settings, never in the database; the connection id is bound in as associated data), only the server decrypts it when a ticket is made, and no API ever returns it (the list only says `hasPassword`). Changing host, port, kind or user name of a connection deletes its stored password, so it cannot be redirected to another target. **Host login (migration 020):** a host can hold one user and one password for all its connections (`hosts.login_*`, encrypted the same way with the host id as associated data); `LoginResolver` picks, per connection, its own login (tick `own_login`), else the host login, else its own data as before. The host password is bound to the addresses the host's connections had when it was saved (`login_targets`), so a new connection to a foreign address never receives it. `ConnectionStore.ResolveLoginAsync` is the one place that decrypts; terminal ticket, Files and desktop ticket all go through it. `HostLoginMigration` adopts existing connection logins at start without deleting anything. Details: [HOSTS.md](HOSTS.md#login-one-user-and-password-per-host). Instead of the variable the server can keep the key in a file: with `JULOS_DATA` set (the image uses `/data`) it creates `secret.key` there once (32 random bytes, readable only by the server) and keeps using it, so a stack needs no secret in its Compose file; the variable wins when both exist. Back up that volume apart from the database. Without a key, storing is off. The price: whoever holds a valid session of the app can open that connection, which is why the login comes first.
- **Open connections follow the session:** every 15 seconds the relay checks that the session (by its stable id, which survives cookie rotation) is still valid, so signing out or ending a session closes its desktop and terminals.
- **Request size:** JSON bodies under `/api` are limited to 64 KiB (4 KiB for login and setup); only `/api/upload` and `/api/upload-file` take more, each with its own limit, at most four at a time. File list and search are rate limited per user.
- **Headers:** strict CSP, `nosniff`, `frame-ancestors 'none'`, HSTS over HTTPS, no referrer.
- **Second factor for actions (step-up, 0.18):** actions that change hosts or files, the access to agents, the account and these security settings need a **fresh authenticator code**; the server checks it before the route (`StepUpPolicy` in `ApiGuard`, answer `403 step_up_required`), the client shows a small sheet and repeats the action. A correct code approves the session for a window (10 minutes by default, 1 to 60 or "every action"; the sign-in counts as the first approval). Same replay protection and lockout as the login. Details: [SECURITY-REVIEW.md](SECURITY-REVIEW.md), "Second factor for actions".
- **Authenticator secret:** sealed in the database with the same AES-GCM box as the target passwords (`enc1:`, the user id as associated data); losing the key loses it too (recovery: `tools/julos-user.sh`).
- **Settings of the instance (0.18):** table `instance_settings` (one JSON value per key, read through `InstanceSettings`, held in memory and replaced on every change, so readers see changes **without a restart**). Today: trusted proxy addresses, allowed target hosts, the second factor, the confirmation mode, writing in the Files app (`security.filesWrite`, env fallback `JULOS_FILES_WRITE`), the preview limit of the Files app (`security.filesPreviewMb`, env fallback `JULOS_FILES_PREVIEW_MB`), the key in the backup and the recovery key (only its wrapped form). The rule of [BACKLOG.md](BACKLOG.md): a setting that matters lives in the app; an environment variable is only the fallback while the app has no value (`SecurityConfig`, `BackupKeys`), and the page shows where the value comes from. Every change is in `security_audit` (who, what, when, no secrets).
- **Sign-in centre (not released):** JulOS is an OpenID Connect provider for the other apps (authorization code with PKCE only, ES256 tokens with `Microsoft.IdentityModel`, back-channel logout when a session ends). The `/oidc/*` endpoints are the one reasoned exception to "every API needs a session"; every one is listed in [SIGN-IN.md](SIGN-IN.md) with its protection.
- **The first account is created on the setup screen**, guarded by the one-time setup code from the server log, so only whoever can read the log can claim the instance. Setup closes after the first account. The console tool (`tools/julos-user.sh`) is the recovery path; passwords are typed in the terminal, never passed as an argument.

## Backup

`BackupWorker` (in the server process, no extra container) writes a dump of the database into a mounted folder every day (no copy of `secret.key` since 0.18: the key wrapped with the owner's recovery key, `secret.key.wrapped`, lies next to it; a plain copy is an opt-in), keeps them for a set time, and `dotnet JulOS.dll backup restore` reads a dump back (all or nothing, in one transaction). The dump is text made by the server itself (`DbDump`: `COPY` blocks of every table in foreign-key order from one snapshot), not `pg_dump`: the image has no client that matches PostgreSQL 18 and `pg_dump` refuses a newer server. The schema is not in the dump; the migrations build it, and a dump naming a migration the server does not know is refused. Optionally (`JULOS_BACKUP_COPY`, off by default) `BackupService` then syncs the new files to a second target behind `IBackupTarget`: a mounted folder (`PathBackupTarget`) or an SFTP server (`SftpBackupTarget` in `JulOS.Workers` over `ISftpSession`/`SshNetSftpSession` in `JulOS.Integrations`, host key remembered at first use and checked after). Both write via a `.tmp` name and rename, apply the local retention to the target, and a failure there is only a status (`backup.copy` in `/api/about`), never a failed local backup. Setup, settings and restore: [BACKUP.md](BACKUP.md).

## First start and connections

- **First start:** with no account the server prints a one-time **setup code** to its log. The browser shows a setup screen asking for that code, a user name and a password,
  then shows the authenticator secret (link and key) and ten recovery codes, and finishes only after a valid authenticator code was entered. Afterwards the setup screen is gone.
  The secret is also drawn as a QR code (made in the browser by `wwwroot/qr.js`, own small encoder, nothing external).
  The console tool `tools/julos-user.sh` stays as the recovery path (reset password or authenticator).
- **Account in the UI** (phone Profil, desktop Einstellungen and the System menu, dialog `#accountDlg`, `wwwroot/account.js`): change the password (`POST /api/auth/password`) and set up a new authenticator
  (`POST /api/auth/totp/begin`, then `/api/auth/totp/finish`). Both need a session and the **current password** every time. A new authenticator key is held in memory for 10 minutes and only replaces the old one
  when its first code is entered (so a mistyped QR scan cannot lock the account out); that step brings new recovery codes (shown once, the old ones are gone). Either change ends all *other* sessions, this one stays.
  Wrong current passwords count per account and per address with the login lockout steps (HTTP 429 with `Retry-After`), the password check runs once at a time per account, bodies are limited to 4 KiB,
  and every step is written to the server log at warning level (`Konto: ...`, with user and address; no secrets).
- **Hosts:** connections belong to hosts (machines or servers), each with its own agent and a status dot from the agent link or a TCP probe; see [HOSTS.md](HOSTS.md).
- **Quick Connect, folders, favourites, settings:** a session without a saved connection, folders and server-side favourites for the connection list, and per-user settings (button layout, theme colour) kept on the server; see [FOLDERS.md](FOLDERS.md).
- **Workspace per device:** table `workspaces` (user, device id from the browser, JSON document with screens, windows, focus, dock, and a version), `WorkspaceRules` checks and rewrites the document, `WorkspaceStore` saves with a version check in one statement, `/api/workspaces` lists, reads, saves and forgets devices; only the user's own data, foreign connections are dropped, rate limited. The desktop interface (`desktop-workspace.js`) saves the windows debounced with the version and restores them at start, connections as "Reconnect" placeholders; see [MULTI-SCREEN.md](MULTI-SCREEN.md#workspace-in-the-interface).
- **Light/dark colour scheme:** Hell / Dunkel / System for desktop and phone, stored as `theme.scheme` in the per-user settings; see [THEME.md](THEME.md).
- **Appearance and icons:** the per-user setting `appearance` (accent colour with a contrast-checked fit, background, dock mode and size, icon size and style, own icon per connection), validated by `SettingsRules` and applied at once through CSS variables (`appearance.js`); one icon family and one mapping from connection, program and host operating system to icon and colour (`icons.js`). See [APPEARANCE.md](APPEARANCE.md) and [ICONS.md](ICONS.md).
- **Connections:** a user keeps a list of connections: name, kind (**Desktop** = RDP, **Desktop (VNC)** = VNC, **Terminal** = SSH), host, port, user name, and for desktops a **domain** and a **keyboard layout**, for both kinds free **notes**. The password is typed per connection (a password manager can fill it) or, on request, stored encrypted (see the security model). A connection for the machine the server runs next to is offered at setup. The target host is chosen by the signed-in
  user, so the server may reach anything the signed-in user names; an optional allow-list in the configuration restricts that.
- **Home:** after login the user sees the list, can add, edit and delete connections, and starts one with a tap. The remote view is the existing client.

## Host information and files

Host information and the shared-folder browser are plain read-only API calls behind the session check (no body, no state). The Files app for hosts over SFTP (below) can also write, behind a switch that is off by default.

- **`GET /api/system/overview`**: CPU load (percent), memory, disk and network rates. `HostSamplerWorker` samples every 2 s (`/proc/stat`, `/proc/meminfo`, `/proc/net/dev`, the file system of the upload folder) and `HostMonitor` turns the counters into rates over the last 6 s at most; a rate needs two samples, so a field is left out (not shown as 0) when there is none or the source cannot be read. The parsers are pure functions on text (`ProcParsers`), tested without Linux.
- **What "host" means inside the container:** `/proc/stat` and `/proc/meminfo` are not namespaced, so **CPU and memory are those of the machine running the Docker daemon** (the server VM), not of a cgroup limit of the container. **Disk** is the file system that holds the upload folder (`JULOS_UPLOAD_DIR`, a bind mount of a folder of that machine in the live setup, so its disk). **Network** is the container's own network namespace: `eth0` of the JulOS container, which means the traffic JulOS itself causes (browser sessions, RDP and SSH relays), not the whole machine's. With `network_mode: host` it would be the machine's. The tile says so.
- **`GET /api/files/list|search|download`**: a read-only file browser for **one** root folder (`JULOS_FILES_ROOT`, default `JULOS_UPLOAD_DIR`; the value `off` switches it off). `FileBrowser` guarantees: paths are relative to the root and `..` is refused; every path is resolved step by step including symlinks (chains, relative targets, loops) and refused when the real result is outside the real root (a link to a target inside the root is fine); names that start with a dot (`.agent`, `.env`) are invisible and unreachable; a download opens the file and then checks where the descriptor really points (`/proc/self/fd`), which closes the gap between check and open; downloads are always `attachment` and `application/octet-stream`, so a stored HTML or SVG file never runs as a page of this address; listings are capped (2000 entries, search 200 hits, 50 000 visited names, depth 16), search never follows links. A named pipe is listed but never opened (the file is opened with `O_NONBLOCK` and refused unless it is seekable, so a FIFO cannot block a thread); list and search are rate limited per user. Not covered: hardlinks (a second directory entry for the same file inside the root). The folder is shared with the target machine's user, so anything that user puts there is visible to the signed-in user; that is the point of a shared folder, and why the root is a single, explicit folder and not the home directory.
- **Files on hosts over SFTP (`/api/files/remote/*`, [FILES.md](FILES.md)):** every SSH connection is a place; the app opens an SFTP session with the **login of the host** (or the connection's own, [HOSTS.md](HOSTS.md#login-one-user-and-password-per-host); or a password typed for that one attempt, never stored or logged), no agent and no root on these places (the separate place "<Host> (Root)" uses the agent, below). `ISftpFileSession` (`JulOS.Integrations/Files`) is the interface (list, stat, stream read, create-new stream, rename, delete, mkdir) with `SshNetFileSession` behind it (the same logon and host key check as the backup target); `FileTransfer` holds the logic (count, atomic write, copy, move, delete, text preview, all with link, depth and count rules) and is tested against an in-memory file system. `RemotePath` normalises paths (absolute only, no `..`). `SftpPool` keeps one session per user and connection for at most 60 s idle and `JULOS_FILES_MAX_SESSIONS` per user; `FileJobs` runs copy, move and delete as jobs with progress and cancel (at most two per user); `FileAuditStore` (table `files_audit`, migration `019`) records every write and every error, never contents or passwords. The host key follows the terminal's column but is stricter (the first key must be confirmed too). Writing is refused unless `JULOS_FILES_WRITE=on`, and every write request needs a server-issued confirmation (`FileConfirmations`, prepare then token).
- **Files as root (`RootFiles`, `RootFileSession` in `JulOS.Frontend/Files`, [FILES.md](FILES.md#root-access-files-as-root)):** a second implementation of `ISftpFileSession` over the agent link (`POST /v1/host/files/*`, blocks of 48 KiB, one at a time) instead of SFTP, so list, transfer, copy between places, jobs, limits, confirmation and history are the same code. The place id is the host id. Every request re-checks the keys (agent online and 0.8.0 or later, level `full`, pause switch, the word the agent reported; the agent and the root helper check the word again) with a 2 s cache; reading a root file also needs a confirmation token and a history entry (fail-closed). The helper in the agent package (`julos-agent-helper.py`) is the only root code: it writes only into new `.julos-*.part` files and renames, never follows a link for a change, and never changes the agent's own files.
- **`GET /api/modules`, `/api/modules/services/*`, `/api/modules/caddy/*`, `/api/modules/ddns/*`**: the Services, Caddy and DDNS modules (off by default: `JULOS_SERVICES`, `JULOS_CADDY`, `JULOS_DDNS` = `off|read|control`; off means `404` and no window or card). No endpoint takes an address from the browser. Services: saved addresses only, allow-list or own network only, checked after name resolution, no redirects, size and time limits, the API key encrypted (`SecretBox`) and never returned. Caddy: read through the admin API (`GET` on four fixed paths), TLS handshakes with the listed domains, configuration text with secrets replaced, access log tail; no write. DDNS: comparison, and with `control` an update of only the named records through a provider adapter (never create or delete), history in `ddns_history`. Details and limits: [MODULES.md](MODULES.md).

## Display engine

A desktop connection is always streamed by the own engine: `ScreenStream` (own RDP client, H.264 through libopenh264) on the server, WebCodecs in the browser,
joined by `/api/remote/screen` and `ScreenRelay`. Terminals do not use it (see "Native terminal"). The picture is H.264, paced by the browser's acknowledgements;
the clipboard carries text, images and files both ways (`ClipboardBridge` on the RDP clipboard channel, see [CLIPBOARD.md](CLIPBOARD.md)); the desktop's sound and the browser's microphone go with it (see Sound below).

Earlier versions of JulOS had a second engine, Apache Guacamole (guacd, tiles through the Guacamole protocol), selectable per connection with an automatic fallback.
It was removed: the own engine is the only way. The column `connections.engine` (migration 004, values `guac` and `stream`) stays in the database as a leftover:
new rows get `stream`, old rows keep `guac`, nothing reads it any more and there is no migration that touches data, so an old connection simply streams.

- **Encoders:** `ScreenStream` talks to `IVideoEncoder` only (`Display/Video`). `EncoderSelector` (settings `JULOS_ENCODER`, `JULOS_CODEC`) picks per session: a VAAPI encoder on the GPU (H.264, or HEVC if the browser reported it in `codecs=` of the WebSocket address and decodes it) or the software `H264Encoder`, which is the fallback for everything, including a GPU that fails during a session. HEVC is agreed on at connect and can be taken back by the browser (message 30). All of it, the settings and the diagnostics (`dotnet JulOS.dll diag encoders`) are in [ENCODERS.md](ENCODERS.md).
- **Availability:** the server grants a desktop ticket only when the H.264 library is present (`ScreenStream.IsAvailable`); otherwise the ticket call answers 503 with the reason. The browser needs H.264 decoding with WebCodecs (`StreamClient.supported()`, needs HTTPS or localhost); without it the session says so instead of trying something else.
- **No fallback:** if a stream session never draws a picture (socket error, closed without a message, no picture within 10 s of the size message, or the decoder failing three times) `app.js` shows a clear message with "Neu verbinden" (`streamFailed`); there is no second engine to swap to. A stream that has shown a picture reconnects as before (session keep, see below).
- **Server-side H.264 (RDPGFX, optional, off by default):** with `JULOS_RDP_GFX=on` the client announces the RDP graphics pipeline and `GfxChannel` (a dynamic channel, `Rdp/Channels/GfxChannel.cs`, PDUs in `GfxPdu.cs`) negotiates version 8.1 with H.264 only. On the first key frame the server sends, `ScreenStream` switches from its own encoder to passing the server's bitstream on as ordinary picture messages (no new message numbers); the browser's acknowledgement of a picture becomes the frame acknowledgement to the server. Anything that cannot be passed on (another codec, painting into the surface, compressed messages, a key frame request from the browser) ends it and the same session is reconnected without the pipeline. Details, limits and tests in [RDPGFX.md](RDPGFX.md).
- **Pacing and acknowledgements:** at most 3 pictures are in flight (`PictureWindow`). The browser acknowledges with the sequence number of a picture, and an acknowledgement covers that picture and every one before it. So a picture the browser never draws (dropped because no decoder was open, lost when the decoder was reopened or failed) cannot leave the window full for good: the next acknowledgement, or the one the browser sends when it drops or loses pictures, clears it. An old acknowledgement after a reset does not count twice, and a number beyond what was sent opens nothing in advance. A key frame request is answered even when the screen stands still and is already sharp. The browser also reopens a decoder that holds pictures for more than a second without drawing them. The server watchdog (2 s without an acknowledgement while the window is full: reset and key frame, with a warning in the log) stays as the last safety net.
- **Slow links (`LinkPacer`):** the window of 3 pictures and the configured bit rate (16 Mbit/s) fit a LAN. On a slow link (WAN, mobile) three full pictures queue up in the socket: measured on a 3 Mbit/s link with 30 ms each way and a noisy 480 x 270 video as load, a click took 1.1 s and 3 pictures a second got through. `LinkPacer` (pure calculation, unit tests simulate a link) watches the acknowledgements: delivery rate (when pictures are sent back to back, bytes per ack spacing), the round trip of small pictures against the smallest of the last 10 s (queue length as the user feels it), how long the socket needed to send a picture (the server side counterpart of `bufferedAmount`; the browser cannot read the server's send buffer, and its own `bufferedAmount` only matters for its uploads, which `sendTransfer` already respects), and whether the encode loop wanted to send but the window was full. When the window is the bottleneck, the pictures are large and much less is delivered than allowed (or small pictures queue, or a send takes more than 60 ms) twice in a row, the allowed bit rate drops to about 85 % of the measured delivery rate (`RateController.SetBitrate`: coarser pictures and, through its own logic, fewer of them) and the window to 2 (1 in a severe jam); when it is calm it recovers 10 % per second and one place per second. Small pictures with a full window only mean a long round trip and change nothing. Result on the same link: median click 0.2 to 0.7 s (four runs, most of them 0.2 to 0.4 s) instead of 1.1 to 1.4 s, 5 to 14 pictures a second. On a 100 Mbit/s link with 60 ms round trip nothing changed (median 114 and 124 ms with the pacer, 92 and 120 ms without). `JULOS_STREAM_PACER=off` switches it off (comparison only). 60 fps mode: dropped. `FramesPerSecond` is only the pace the rate controller assumes, it caps nothing, and the test desktop (xrdp) delivered about 26 updates a second to a 60 Hz source with 30 and with 60 alike.
- **Certificate of the RDP target (trust on first use):** RDP servers present a certificate they made themselves, so it cannot be checked against a CA. Instead the SHA-256 fingerprint of the certificate (`SHA256:AB:CD:...`, as `openssl x509 -noout -fingerprint -sha256` prints it) is stored per connection (`connections.cert_fingerprint`, migration 006) on the first successful logon, and every later handshake must show the same one (`CertificateTrust`, `CertificatePolicy`; same rules as the SSH host key). The check runs inside the TLS handshake (`RdpOptions.CertificateCheck`), before CredSSP, so a changed certificate stops the connection before the user name and password leave the server. The browser then gets error 800 (`ScreenProtocol.CertificateChanged`: fingerprint now and fingerprint before) and shows the German warning dialog (`RemoteSession.certDialog` in `app.js`): "Abbrechen" ends the session, "Neuem Zertifikat vertrauen" repeats the ticket request with `acceptCert` set to exactly the shown fingerprint (a confirmation for any other fingerprint does not count, and it is used for that one attempt only); the new fingerprint replaces the old one after the logon succeeded. The fingerprint is stored only server side; `GET /api/connections` and the connection dialog never carry it, it appears only in the warning. Changing host, port or kind of a connection forgets it (it belonged to the old target). Windows regenerates its self-signed RDP certificate from time to time, so expect the dialog after such a renewal.
- **Session keep and drives:** the RDP session belongs to the server, not to the WebSocket: when only the browser's connection drops, `ScreenRelay` keeps it (paused, events dropped) for `JULOS_STREAM_KEEP_SECONDS` and a new WebSocket with the session token re-attaches, with a key frame and without a new login ([SESSIONS.md](SESSIONS.md)). `RdpdrChannel` can announce one file system device rooted at `JULOS_DRIVE_ROOT`; `DriveService` answers its requests behind the `DriveJail` fence, read only unless the connection's second switch says otherwise ([DRIVES.md](DRIVES.md)).
- **VNC (`Display/Vnc`):** a second source for the same pipeline. `ScreenStream` reads its picture through `IScreenSource` (the framebuffer, the input calls, `ConnectAsync` and `RunAsync`); `RdpClient` and `VncClient` both implement it and report changes to `IScreenHandler`, so the encoder, the refinement, the browser protocol and the status bar are shared and RDP behaves as before. The RFB client reads on a thread of its own with blocking reads, decodes into a private canvas and copies finished rectangles into the framebuffer under `FrameLock`; keys come as X11 keysyms (browser message 18). Kind `vnc` has its own connection rules (port 5900, no domain or drive) and, unlike the others, may have an empty password. Details and limits: [VNC.md](VNC.md).
- **Lossless refinement of still parts (`Display/Refine`):** H.264 in the browser is 4:2:0, so one-pixel coloured strokes (syntax-coloured text, coloured terminal output) are never pixel sharp, whatever the quantiser (a 4:4:4 stream is not an option: libopenh264 encodes 4:2:0 only, and phone decoders do not take High 4:4:4). `TileRefiner` keeps a grid of 32 x 32 tiles with the time of their last change. A tile that has been quiet for 120 ms (and only while the browser keeps up: at most one picture in flight, paced by a bucket of 25 % of the bit rate) is sent again losslessly as a palette PNG (`TilePng`; tiles of the same row are joined up to 640 px; a rectangle with more than 256 colours - photo, video - is not sent, that belongs to the stream). Server to browser message 40 carries the rectangle and the PNG; `stream.js` draws it on a second canvas above the video. When a refined tile changes again, message 41 (list of rectangles) tells the browser to clear it right before the picture with the change goes out, so an old overlay never stays over new content. Both go through the same ordered socket as the pictures, and the browser applies them in order (`overlayChain`). No extra server CPU was measurable and the latency under motion is unchanged (numbers in [IDEAS.md](IDEAS.md), 2026-11-19). `JULOS_STREAM_REFINE=off` on the server and `localStorage` `pd.refine` = `"off"` in the browser switch it off (comparison only). Old browser code ignores the new message numbers.
- **Keyboard layout and domain per desktop connection** (migration 009, columns `domain`, `notes`, `keyboard_layout`, all with defaults so old rows and old backups keep working): the layout code (`de` default, `de-at`, `de-ch`, `en-us`, `en-gb`, `fr`, `es`, `it`, list in `Logic/KeyboardLayouts.cs`) becomes the Windows layout id in the RDP client info (`RdpOptions.KeyboardLayout`, before: always `0x407`), the domain goes to `RdpOptions.Domain` (a domain in the user name field, `DOMAIN\user`, still works; a separate field wins). The ticket answer carries the key style for the browser (`layout`: `de`, `qwertz`, `qwerty`, `azerty`): Ctrl chords use the key the letter has on that layout, characters are sent as Unicode, and only on `de` the umlauts go through their German keys (xrdp takes no Unicode for them). Known limit: no layout-aware chords for punctuation, Spanish and Italian count as QWERTY.
- **Mouse and keyboard input:** all five mouse buttons go through (message 3: 0 left, 1 middle, 2 right, 3 back, 4 forward; back and forward are the extended RDP mouse events), the wheel is message 4 with a signed 16-bit amount in Windows units (120 a notch, finer steps pass as they are; `mouse.js` scales pixels, lines and pages and carries the remainder to the next event) and a flag for the horizontal wheel (positive: up or right). `StreamClient` remembers which keys and buttons are down and releases them at the target when the window loses the focus or the tab is hidden (otherwise Alt after Alt+Tab stays pressed there). In full screen `app.js` asks the browser for the keyboard lock (`navigator.keyboard.lock`, Chrome and Edge only, secure context only, only in full screen) so Esc, Alt+Tab, the Windows key and Ctrl+W/T/N go to the target; holding Esc still leaves full screen.
- **Wire protocol:** binary, documented in `ScreenProtocol.cs` and the header of `stream.js`. The clipboard is message 6 (server to browser, UTF-8 text, the remote desktop copied) and message 9 (browser to server, UTF-8 text, up to 1 MiB; the remote desktop fetches it when it pastes). `stream.js` presents it to `app.js` as `onclipboard(text)` and `sendClipboardText(text)`, so the clipboard dialog is shared. Message 16 (browser to server, 1 byte: 1 pause, 0 resume) is sent for a session that is in the background. Images and files have their own messages (7 to 10 to the browser, 10 to 15 from it: chunked, with sizes and names checked on both sides) and callbacks (`onclipimage`, `onclipfiles`, `sendTransfer`, `fetchFile`); the layout is in [CLIPBOARD.md](CLIPBOARD.md).
- **The agent is independent of the display engine.** `/api/agent/*` (health, windows, apps, launch, mode) and the window bar talk to the agent (agent link or Unix socket, see "The agent link") and never see the picture path (checked on the test instance: health, window list, launch, window bar).

## The agent link (agents on other machines)

The agent API used to work only when the server and the desktop ran on one machine (Unix socket in a shared folder). The agent now also connects **outbound** to the server, so the
window bar, the launcher and photo/file/clipboard work for desktops anywhere. Protocol, enrolment and security properties are in [AGENT_API.md](AGENT_API.md); the design in short:

- **One agent per host.** A host (table `hosts`, see [HOSTS.md](HOSTS.md)) is a machine with its own saved connections; the agent belongs to it and serves all its connections. Tables `agents` (host id, user id, SHA-256 of the token, last seen, version, platform, host name and system as the agent reports them) and `agent_codes` (SHA-256 of a
  one-time code, 10 minutes, one use). `AgentStore` (Backend) holds the SQL, `AgentCredentials` the code and token format.
- **`AgentLinks`** (Integrations, singleton) holds the live WebSocket of each agent, found only by host id *and* owning user. `AgentLink` is request/response with ids over
  the socket plus chunked binary frames for data (back pressure comes from awaiting each frame; one transfer at a time per agent; 15 s per frame, 3 minutes in total; 14 MB image, 64 MB file).
  `LinkTransfers` does the checks (image header, file name, extension, size) before anything is sent and maps the agent's answer to the same outcomes as the shared-folder uploaders.
- **`AgentRouter`** (Frontend) picks the transport per call from `?c=<connection id>` (its host) or `?h=<host id>`: link if connected; "offline" (no answer, never the socket) if one is enrolled but gone; otherwise the
  Unix socket as before (also without `c`). The browser can only trigger the fixed requests of `AgentEndpoints`; the server sends nothing the browser chose freely.
- **Authentication:** `/api/agent-link` (WebSocket, `Authorization: Bearer`) and `/api/agent-link/enroll` are outside the session check (`ApiGuard.IsAgentPath`) because the agent is not a browser; they check
  the token or the one-time code themselves and are rate limited. Everything that manages agents (create code, remove, status) needs the normal session.
- The three agent files are served by the server (`/agent-files/<name>`, a fixed allowlist, copied into the image), so what runs on the machine matches the server's version.
- **Sound.** Output: `SoundChannel` (RDPSND) takes 16-bit PCM and nothing else (no decoder on the server; every server has PCM, the list is sorted 48000 Hz stereo, 44100 Hz stereo, then the rest) and raises the blocks; `AudioBridge` queues them for the WebSocket sender and `ScreenRelay` sends them as message 20 (channels, rate, server time, PCM). The queue is **bounded** (`AudioBridge.MaxQueuedMs`, 200 ms; the oldest block is dropped), so a stalled or hidden tab never makes the server buffer audio; every block is confirmed to the remote desktop whatever happens to it. Sound is **off per connection until the browser sends message 20 "on"**, which it does only while its `AudioContext` is running (so a suspended tab asks for nothing). In the browser `stream-audio.js` hands the blocks to an AudioWorklet (`stream-audio-worklet.js`: ring buffer, linear resampling to the context rate, jitter buffer with a 60 ms target that grows to 200 ms after an underrun and shrinks again, up to 3 % faster playback to work off a backlog, drop above target + 150 ms; no per-sample code on the main thread). Menu entries "Ton vom Rechner" (on/off, remembered), "Lautstärke" (steps) and "Mikrofon". Windows only talks RDPSND to a client that also announces `rdpdr`, so `ScreenStream` registers an `RdpdrChannel` without devices. Input: `AudioInputChannel` (MS-RDPEAI, dynamic channel `AUDIO_INPUT`) answers version and formats (16-bit PCM only, mono before stereo, rates up to 48 kHz first), confirms Open and Format Change, and sends the microphone in packets of the size the server asked for, each announced by an Incoming Data message. The browser captures mono at the rate the server announced in message 21 (`getUserMedia` with echo cancellation, noise suppression, auto gain; an AudioWorklet averages down to that rate and returns 20 ms chunks), sends them as message 21, and `AudioBridge` converts to the server's format (`PcmResampler`, linear). The microphone is off until the user picks it in the menu (browser permission prompt), a red "Mikrofon an" pill shows while it is live. The server asks for sound only when a program on the desktop records: Windows opens the channel at logon, **xrdp opens it only when a program starts recording**, so the menu cannot know beforehand whether a desktop offers a microphone; it says "wartet auf Programm" until recording starts. **With several sessions** every stream session has its own `StreamAudio` (own `AudioContext`, own server-side switch); only the visible, active session plays (`RemoteSession.applyAudio`, called on show/hide and on every activation; the others tell the server "off", so it sends and buffers nothing), the volume and on/off choice are shared. The microphone belongs to **one session at a time** (`StreamAudio.micOwner`): starting it in a second session is refused with a message naming the first, and one red pill for the whole page (`#micLive`, shows the session's name) stays visible even when that session is in the background. The menu entries are in the session menu on the phone (the dock menu) and in the menu "Sound" of the menu bar on the PC (the dock is not shown there; the same actions through `remoteApi.audio`); VNC sessions have no sound and say so in both. "Sound and microphone: diagnosis" (`audiodiag.js`) shows channel, playback, level, microphone and permission state. A browser that takes over a kept session is sent the sound status again (the bridge only reports changes). See [AUDIO.md](AUDIO.md). Messages 20 and 21 (both directions) live in their own number range (from 20) next to the picture messages.

## Several sessions at once

Contract, caps and UX are in [SESSIONS.md](SESSIONS.md). In short: the browser makes one object per open session (`RemoteSession` in `app.js`, a `Session` from `sessions.js`) and generates a session id (`sid`). The ticket carries it; the server slot is `user:connection:sid` and `SessionRegistry` (`JulOS.Integrations`) enforces the replace-only-yourself rule and the per-user cap (`JULOS_MAX_SESSIONS_PER_USER`, default 8; status 797 with a German message) for Guacamole and the stream engine alike.
Background sessions: the browser sends message 16 (pause) and the server stops encoding until it is lifted (the encoder keeps its reference, so the next picture is an ordinary delta with everything that changed).
## Native terminal (SSH)

A connection of kind **Terminal** is not a picture: the server holds the SSH connection and the browser draws real text with xterm.js, so selection, copy and
paste, scrollback and fonts are the browser's own. Terminals never went through the display engine's RDP path; they have their own SSH relay.

- **Backend:** `JulOS.Integrations/Ssh`. `ISshSession` (connect with password, host key callback, read, write, resize) with one implementation, `SshNetSession`
  (SSH.NET: password and keyboard-interactive login, pseudo-terminal `xterm-256color`, keep-alive every 30 s, the shell is read on its own thread through a bounded channel so a slow browser
  throttles the target through the SSH window). `SshRelay` joins a WebSocket and a session. SSH.NET is the one place that knows the library; replacing it means writing another `ISshSession`.
- **Endpoint:** `POST /api/remote/ticket` for a terminal connection answers `engine: "ssh"` and a one-time ticket (`SshTickets`, 30 s, per user, in memory; the request carries `cols`, `rows`, `sid`, and optionally `acceptHostKey`).
  `GET /api/remote/ssh?ticket=` upgrades to a WebSocket (same checks as the other two: session, own origin, ticket). The relay ends when the app session ends (checked every minute), like the other relays.
- **Wire protocol** (binary, first byte = kind; `SshProtocol.cs`, `terminal.js`): browser to server `1` data, `2` size (u16 cols, u16 rows), `3` ping, `4` pause, `5` resume;
  server to browser `1` data, `2` ready (JSON: `hostKey` = `new`, `known` or `changed-accepted`, `fingerprint`), `3` end (JSON: `code`, `message`, for a changed key also `fingerprint` and `previous`). Pause/resume is flow control: the browser asks the
  server to stop reading the shell when it has more than 256 kB it has not drawn yet (a WebSocket has no back pressure of its own). Input messages are limited to 64 kB (the page sends 16 kB pieces).
- **Limits and sessions:** the shared `SessionRegistry` (see [SESSIONS.md](SESSIONS.md)): one WebSocket per slot (user, connection, browser session id; a new one for the same slot replaces the old one, whose shell on the target ends with it), `JULOS_MAX_SESSIONS_PER_USER` per user, and 32 terminals at the same time in total. There is no extra idle timeout: like the other relays, an open session ends with the app session or the browser connection (a shell that is open but idle is the user's business).
  Error codes are the ones the screen stream uses where they exist (513 busy, 514 timeout, 515 failed, 520 unreachable, 769 login refused, 777 taken over, 797 too many sessions) plus 800 host key changed, 801 shell ended, 802 app session ended. All texts are German and never contain the password.
- **Host key (trust on first use):** the SHA-256 fingerprint of the host key, `"<algorithm> SHA256:<base64>"` as `ssh-keygen -l` prints it, is stored per connection (`connections.host_key`, migration 005).
  First connection: the key is accepted and stored *after* the login succeeded (a target whose password does not fit is not pinned) and the page says so. Later connections: the same key is silent. **A different key is never accepted silently**: the relay refuses before sending the password (end code 800 with both fingerprints), the page shows a warning dialog
  and only the button "Neuen Schlüssel vertrauen" repeats the ticket request with `acceptHostKey` set to exactly the shown fingerprint (a confirmation for any other key does not count); then the new key replaces the old one. Changing host, port or kind of a connection forgets the key (it belonged to the old target); the key is never sent to the browser except as the fingerprint in the warning.
  Key algorithm changes count as changes (the same server offering another algorithm first would show the dialog once). Not covered: a key that is *already* in the database from a man in the middle on the first connection (TOFU's known limit; compare the fingerprint shown with the one on the target).
- **Password:** typed per connection or stored in the same encrypted store as for RDP (nothing new is stored); it only lives in the ticket (30 s, memory) and in the SSH handshake. Key-based login is not built (see IDEAS).
- **Browser:** `terminal.js` (`TerminalView`: xterm.js, WebGL renderer when available, fit, unicode 11, font stack, theme from the app tokens, scrollback 10 000 lines, selection and copy/paste, mouse reporting, flow control, host key dialog) and `terminal-session.js` (`TerminalSession`, the session kind for `Sessions`; it extends `RemoteSession`, so key bar, menu and overlay are the ones of the remote view).
  Size follows the container: xterm fits locally at once, the new columns and rows go to the server (SSH `window-change`) 180 ms after the last change, so a keyboard animation does not flood the target; the terminal never changes the size of its container, so there is no feedback loop. Phone: the page's own input field (`#kb`, the proven Gboard handling) types, the key bar sends X11 keysyms that `keysymBytes` turns into bytes (arrows follow the application cursor mode, modifiers use the xterm parameter form); drag scrolls (as scrollback, as arrow keys in vim/less, as mouse wheel for programs with mouse support), long press selects a word and drag extends it, a small menu copies and pastes, two fingers change the font size. Desktop: xterm takes the keys directly, Ctrl+Shift+C / Ctrl+Insert copy, Ctrl+Shift+V / Shift+Insert paste, Ctrl+C copies when there is a selection and is ^C otherwise, right click opens the copy/paste menu.
- **Program sessions:** a terminal connection can start `claude`, `codex` or a custom command instead of the bare shell, in a working directory and optionally inside tmux (`program`, `workdir`, `keep_alive`, `custom_command`, migration 014). After login the relay opens a second short channel beside the shell (`ISshSession.ExecAsync`, 5 s, hence `MaxSessions` 2), probes program, directory and tmux with a fixed command, and writes one start line into the shell built from fixed templates and validated fields with single-quote quoting (`SshLaunchRules`); anything missing falls back to a plain shell with a visible notice, never silently. The `ready` message then also carries `program`, `keep` (`tmux`) and `notice`. The program is taken from the stored connection only, never from the ticket request, and a custom command is never logged. Details: [CLI-SESSIONS.md](CLI-SESSIONS.md).

## Network tools (ping, DNS, port test)

`POST /api/tools/ping`, `/api/tools/dns`, `/api/tools/ports` and `GET /api/tools/targets` (dialog `#netDlg`, `wwwroot/nettools.js`; phone: Profil, desktop: menu System). They measure from the server, not from the browser.
There is **no free input for addresses**: a target must be the host of one of the user's saved connections *and* pass `JULOS_ALLOWED_HOSTS` (`NetToolRules`), so the server cannot be used as a scanner or a resolver for arbitrary
targets beyond what saving a connection already allows (SECURITY-REVIEW Nr. 1). Ports: 1 to 10 per call, TCP connect only (no bytes sent), `open`, `closed` (refused) or `filtered` (no answer in 1.5 s). Ping: ICMP echo without special rights
(no custom payload: that needs privileges; a container needs `net.ipv4.ping_group_range` to allow it, which Docker sets by default), 1 to 8 echoes, 2 s each; where it is not possible the answer says so and the port test still works.
DNS: the system resolver (A and AAAA, no other record types), 4 s. Every call needs a session and the `X-JulOS` header, is limited to 30 a minute per user, at most 4 run at once on the server, and is logged (tool, target, user).
`JULOS_NETTOOLS=off` switches all four routes off (404).
