# Files: the shared folder and every host over SFTP

The Files app (desktop window and phone page "Dateien") works like an explorer (selection, keys, context menu, drag and drop, a tree of hosts with pinned folders, a simple editor): see [FILES-EXPLORER.md](FILES-EXPLORER.md). It shows **places**:

- **Gemeinsamer Ordner** (shared folder): the one folder of the JulOS server (`JULOS_FILES_ROOT`, default `JULOS_UPLOAD_DIR`). Read only: view the list, search by name, download. This is the old behaviour, unchanged; see [ARCHITECTURE.md](ARCHITECTURE.md) for its guarantees.
- **Every host with an SSH connection**: the files of the SSH user, over **SFTP**, with the **login of the host** (or, if the connection asks for its own, the credentials saved at the connection). List, view text, download, upload (pick or drag and drop), new folder, rename, copy, move (also from host to host through the server) and delete.
- **"<Host> (Root)"**, only for a host whose agent allows it: the same functions **as root**, through the host agent (no SSH, no password). Off unless you switch it on in three places, see [Root access](#root-access-files-as-root).

A connection that is not SSH (RDP, VNC) is not a place. A host with several SSH connections offers a choice ("Host · Connection"). On an SSH place what you can do is what the SSH user can do; only the separate place "<Host> (Root)" works as root (below).

## What it needs

- An SSH connection (kind **Terminal**) with a host and port. The credentials are those of [the host login](HOSTS.md#login-one-user-and-password-per-host): its user and password when the host has them (**no question**), or the connection's own when it has the tick "Eigenen Benutzer verwenden".
  The Files app never asks for a password the host login already holds.
- If the host has a login with a **user but no password**, the dialog asks only for the password (the user is shown) and offers **Für diesen Host speichern** (a tick, off by default): the password is saved as the host's password only **after the logon worked** (`saveForHost` in `POST remote/open`; the answer says `hostLoginSaved`), encrypted, bound to the connection's address, written to the host history. Without the tick, and for any other case without a saved password, the typed password is used for that one connection, **never stored and never logged**.
- SFTP enabled on the host (the OpenSSH default `Subsystem sftp`). Otherwise the app says so (`sftp_unavailable`).
- Reading works out of the box. **Writing is off by default** and has to be switched on, see below.

### Switching writing on

Everything that changes something (upload, overwrite, rename, move, copy, delete, new folder, and the `prepare` before it) is refused with `403 write_off` until you switch it on **in the app**: Settings, Security, **"Write files"** (`PUT /api/security/files-write`, stored in `instance_settings` as `security.filesWrite`, changed only with a fresh authenticator code like every security setting, written to the security history). It takes effect on the next request, **without a restart**.

The environment variable `JULOS_FILES_WRITE=on` (server container) is only the **fallback**: it counts while the app has no value ("Reset to default" in the app forgets the app's value again). The value of the app wins in both directions: the app can switch writing off although the environment says `on`. A typo in the variable (anything but `on` or `off`, including `true` or `1`) is **off**, and never switches writing on. The settings page shows where the current value comes from (app, environment, default).

With writing off the page does **not** grey out the buttons silently: a note above the list says so and has the button **"Zum Schalter"** (it opens Settings, Security, at this switch), and a click on a write action (New, Upload, Rename, Delete, Cut/Copy, drop of files) explains it in a dialog with the same button. Reading, viewing and downloading still work. A refused attempt is written to the history. The switch changes nothing about the safeguards: every action still needs its confirmation (`prepare`, token, 60 s), the root place its own keys (below), and the pause switch stays.

Other settings: `JULOS_FILES_MAX_MB` (largest file and largest operation, default 2048, range 1 to 65536) and `JULOS_FILES_MAX_SESSIONS` (open SFTP connections per user, default 4, range 1 to 16).

## Security model

**Second factor (0.18):** every write and every root read starts with `POST /api/files/remote/prepare`, and that step needs a fresh authenticator code of the session (`403 step_up_required`); the second step with the token needs nothing more. Reading, listing and downloading on non-root places are unchanged. See [SECURITY-REVIEW.md](SECURITY-REVIEW.md), "Second factor for actions".

| Rule | How |
|---|---|
| **Everything needs the session.** | All `/api/files/remote/*` routes sit behind `ApiGuard`: session cookie, and for every `POST` the header `X-JulOS: 1` and a matching `Origin`. Rate limits per user and minute (list 240, text 120, transfers 60, writes 120, open 20, plan 60). |
| **The host key is never accepted silently.** | The first connection shows algorithm and SHA-256 fingerprint and needs your explicit confirmation (`host_key_new`); the key is then saved in the connection (the same column the terminal uses, so both agree). A **changed** key stops with a warning that shows the known and the new key (`host_key_changed`); only an explicit second confirmation replaces it. This is stricter than the terminal, which remembers the first key without asking. |
| **Paths are normalised on the server, absolute only.** | `.` and empty parts are dropped; a relative path, `..`, control characters, more than 4096 characters or 128 parts are refused (`invalid_path`). An empty path or `~` means the home directory of the SSH user. New names must be one plain segment (no `/`, not `.`/`..`, no control characters, at most 255 bytes). Names with control characters or a `/` on the host are hidden from listings (and counted): a compromised host could otherwise list `../../x` and make a copy to another host write outside the chosen folder (SECURITY-REVIEW F-24). Names the host lists are never used as paths unchecked, also in copy, move and delete. |
| **Only what the SSH user may do.** | JulOS adds no rights. `denied` is shown as such. |
| **Links are shown and never followed.** | A symbolic link is listed as a link, with its kind (to a file, to a folder, broken). Counting, copying and deleting do not follow links: deleting a folder removes a link inside it as a link, never what it points at; copying skips links (a link to a **file** that you select directly is copied as that file). SSH.NET offers no `readlink`, so the target *path* is not shown. The SFTP library follows a link when it is given a path (delete, rename and `Get` would hit the target), so the app deletes and renames links through the handle of the directory listing, and it never replaces a link as a target (`target_is_link`); a real test against the dev SSH target checks that the target of a link survives. |
| **Size and count limits, nothing in memory.** | Lists: 2000 entries (`truncated`). Copy and delete: at most 10 000 entries and 20 levels, counted **before** anything changes. Download and upload stream in 128 KiB pieces and never hold a whole file; a transfer larger than `JULOS_FILES_MAX_MB` is cut and cleaned up, and a copy stops when the bytes actually received exceed it (a host that announces small sizes cannot get more through). Text view: first 1 MiB. |
| **Never a page.** | Downloads are always `attachment` and `application/octet-stream` (plus `nosniff`); there is no HTML or SVG preview. The text view sends the text as a JSON value and the page sets it with `textContent`. Binary files (a NUL byte in the first 8 KiB, or no valid UTF-8) are refused as text (`not_text`). |
| **Writes need a confirmation issued by the server (two steps).** | Like the host actions: first `POST remote/prepare` checks everything and answers with a **token** and a readable summary (host, target host, paths, counts, size, names that would be replaced, a folder with content); the page shows exactly that. Only then the action itself (`upload`, `mkdir`, `rename`, `delete`, `copy`) runs with the token. The token is valid for **60 s**, **once**, and bound to the **session**, the **action** and the **exact request** (connection, source paths, target, name; the count follows from the paths). A changed path or action, another session, a reuse or an expiry is refused (`confirmation_mismatch`, `confirmation_invalid`, `confirmation_expired`; a refused token is used up). Only its SHA-256 is kept in memory, at most 20 open per user. An upload confirmation covers exactly the prepared file names, each once. **Overwriting** and **deleting a folder with its content** stay a second explicit step: the run may only ask for `overwrite` or `recursive` if the server showed it in `prepare` (otherwise `confirmation_mismatch`); the server never replaces anything otherwise (`exists`). **How much you must confirm depends on a level the server computes in `prepare`** (the same `ConfirmPolicy` as for host actions, see [HOST-AGENT.md](HOST-AGENT.md#the-confirmation-two-steps-on-the-server)): `confirmLevel`, `confirmMode`, `confirmWarn`, `confirmCritical`, `typeToConfirm` (the connection's name, only in mode `type`) are in the answer. **Routine** (one file: upload, rename, new folder, copy, move, delete; reading a root file; overwriting on a normal SSH place, which the sheet shows) needs only the tap on the button. **Dangerous** (delete several items, a folder with content, anything as root, overwrite on a root place) needs the tick "Ich habe die Warnung gelesen" (or the typed name, by the setting in Settings, Security). **Very dangerous** (delete, rename or move a path right under `/` or a home folder on a root place) adds a red line and never drops below the tick. The run sends `acknowledged` (and `typed`; for an upload as query parameters, for every file) and the **server refuses with `400 confirm_required`** without it, the token staying valid. The history entry `started` carries `level:mode`. There is **no recycle bin**. The root `/` is never deleted. |
| **Every write and every error is in the history, fail-closed.** | Table `files_audit` (migration `019`). Before the first writing step an entry `started` is written; **if it cannot be written, nothing is executed** (`audit_failed`, as with the host actions); the result (`ok`, `failed`, `cancelled`) follows as its own entry, and a job only counts as finished after its result entry is stored. Columns: user, host (the name of the connection), action, path (shortened to 300 characters, control characters replaced), result (`ok`, `failed`, `denied`, `cancelled`), detail code, number of items, time. **Never contents, never passwords.** The last 2000 rows per user are kept; the history survives deleting the connection. The page shows it under the clock icon (`GET /api/files/audit`). |
| **Sessions are short-lived and pooled.** | One SFTP session per user and connection, shared by all requests, closed after **60 s without use**, when the connection drops, **when the connection is edited or deleted, and at sign-out, "sign out all others" and a password change** (an unused session at once, one with a running job when the job ends; never handed out again); at most 4 per user (the longest unused closes first, otherwise `too_many_sessions`). While a place is open the page keeps it alive. A session never holds the password; after it closed, a connection without a saved password asks again. **Changing or removing the host login closes the pooled sessions of all connections of that host.** |

## The API

All paths are under `/api/files/`. Errors are `{"error": "<German text>", "code": "<code>"}` (plus `fingerprint`, `algorithm`, `known` for host key problems); the page translates the code.

| Method and path | What |
|---|---|
| `GET info` | `{local, write, maxBytes}` |
| `POST remote/open` | `{connection, password?, acceptHostKey?, saveForHost?}` opens (or keeps alive) the session; `{home, hostKey: known\|remembered\|replaced, fingerprint, algorithm, hostLoginSaved?}`. Errors `password_required` (with `user` and `canSave` when the host login has a user but no password), `logon_failed`, `host_key_new`, `host_key_changed`, `unreachable`, `timeout`, `sftp_unavailable` |
| `POST remote/close` | `{connection}` |
| `GET remote/list?c=&path=` | entries (`name`, `path`, `kind` = file/directory/link/other, `size`, `modified`, `mode`, `resolved`, `openable`), directories and links to directories first, natural order; `truncated`, `hidden` |
| `GET remote/text?c=&path=&token=` | `{path, text, truncated, size}`; the `token` only on a root place |
| `GET remote/download?c=&path=&token=` | the file, streamed; the `token` only on a root place |
| `POST remote/prepare` | step 1 of every write (on a root place also of `text` and `download`): `{action: upload\|mkdir\|rename\|delete\|copy\|move\|text\|download, connection, paths?, dir?, name?, names?, target?}`; checks like the action would, changes nothing; answers `{token, expiresIn, action, host, targetHost?, paths, dir?, name?, names?, files, directories, links, bytes, conflicts, nonEmpty}` (`conflicts`: names that exist at the target and would be replaced; `nonEmpty`: a folder with content is included) |
| `POST remote/upload?c=&dir=&name=&overwrite=1&token=` | raw body; written under a temporary name, then renamed; the token covers the prepared names, each once |
| `POST remote/mkdir`, `remote/rename` | `{connection, dir, name, token}`, `{connection, path, name, overwrite?, token}` (rename stays in the same folder) |
| `POST remote/delete`, `remote/copy` | `{connection, paths, recursive?, token}` and `{connection, paths, target: {connection, dir}, move?, overwrite?, token}` (`move: true` needs a `move` prepare); answer `202 {job}` |
| `GET remote/jobs/{id}`, `POST remote/jobs/{id}/cancel` | state (`running`, `done`, `failed`, `cancelled`), progress (items and bytes, current name), counts, skipped links and skipped existing files |
| `GET audit?limit=` | the history |

Copy, move and delete run as **jobs** (at most two running per user; finished ones stay for ten minutes). The page polls the job and can cancel it.

## Root access (files as root)

The place **"<Host> (Root)"** shows and changes the files of a host **as root**, through the host agent ([HOST-AGENT.md](HOST-AGENT.md)). It exists because the SSH user often cannot read or change exactly the files you came for (`/etc`, `/var`, another user's home). It is therefore the most powerful thing in JulOS next to the terminal as root, and built like the host actions: every key must agree, every step is confirmed, nothing happens silently.

**The keys (all of them, checked again on every single request, also between two blocks of a transfer):**

1. The agent of the host is **online** and is version **0.8.0 or later** (`root_offline`, `root_outdated`).
2. On the page "Hosts", the level of this host is **"Alles"** (`full`; `updates` and `read` do not give files, `root_off`).
3. The **pause switch** for host actions is not on (`root_paused`; the same switch as for the other actions).
4. The agent allows it **locally**: the word `files-root` in `/etc/julos-agent/permissions` (installer: `--allow files-root`; `root_not_permitted`). The root helper checks the file once more.
5. Writing needs the switch "Write files" as everywhere (`write_off`); reading a root file does not.

The place appears in the app only when 1 to 4 hold at that moment (the page knows the agent state); a refusal later says which key is missing. The place's id is the host's id; the name is "<Host> (Root)" and the page marks it red: a banner in the list, a red mark under the path, and a root notice in every confirmation dialog.

**Confirmation (two steps, like F-25).** Every writing action (upload, overwrite, new folder, rename, copy, move, delete) first goes through `POST remote/prepare` and then runs with the one-time token (60 s, bound to session, action and exact request), exactly as for SFTP places; on a root place every delete and every overwrite is **dangerous** (the tick), a path near the root very dangerous (see above); a copy **to** a root place counts as root (the dialog and the audit entry say "<Host> (Root)"). Unlike an SSH place, **reading** also needs this: **download** and **text view** of a root file are prepared (`action: download` or `text`, one file), confirmed in a dialog that names the file and says "as root", and then run with the token. Without a valid token the server answers `confirmation_invalid` and the agent is not asked. The list itself (names, sizes, modes) is not confirmed; it is behind the keys and the session.

**History, fail-closed.** Every write and every read of a root file writes `started` into `files_audit` first; if that fails nothing happens (`audit_failed`). The place is named "<Host> (Root)" in the entry. No content, no token.

**Transport.** The server talks to the agent over the existing agent link, in **blocks of 48 KiB** (Base64 in JSON, so about 64 KiB per message, the agent accepts 70 KiB). One block at a time: the next request goes out only when the previous answer has been taken, so a slow browser slows the transfer instead of filling memory (back pressure); nothing but one block is held. Each block asks for the keys again (cached for 2 s). The agent forwards to the root helper (one connection per request, see HOST-AGENT.md). A lost link, a revoked key or a refusal in the middle ends the transfer with an error and the temporary file is removed; an incomplete download aborts the connection, it never looks complete.

**What the root helper does and never does.** It resolves the parent folder once and then works with file descriptors relative to it and `O_NOFOLLOW` on the last name, so a link swapped in as the last name cannot redirect a write, rename or delete. It **writes only into a new file named `.julos-<12 hex>.part`** (created exclusively, with `pwrite` at the expected offset) and then **renames** it over the target; it keeps the owner and mode of a replaced file (a new file gets 0644), and refuses to replace a link or a folder (`target_is_link`, `type_mismatch`). A link is never followed for changes (listed as a link, never copied, deleted or replaced as a link, never written through); **reading** a link reads the file it points to, as root, like the stat of an SFTP place (F-32). The root `/` is never deleted (`root_forbidden`), and what makes the agent itself is **protected**: `/etc/julos-agent`, `/usr/local/libexec/julos-agent`, `/opt/julos-agent`, `/var/lib/julos-agent` can be listed and read but never changed (`protected_path`), so the agent cannot be used to give itself more rights. The check runs on the path as sent **and again on the real folder after all links are resolved**, so a link elsewhere that points into one of these folders does not get around it (tested). Not covered: a bind mount of such a folder somewhere else.

**Limits and honest edges**

- Root is root: with the word, the level and a confirmed dialog you can delete `/etc` or fill the disk. The confirmation names the path and says "as root"; it does not judge the target. There is no recycle bin.
- Files on a root place are plain files: no owner, mode or time is copied from another place; a replaced file keeps its own owner and mode.
- A named pipe or device is listed as "other" and never opened for reading (read refuses everything that is not a regular file).
- A recursive delete or copy lists a folder first and then works on names (as for SFTP, F-28): a local user who can write in that folder can swap things in between. As root that is worse than as a normal user; do not recurse in folders other users can write to.
- The installer opens the helper's sandbox for this word (no `ProtectHome`, no private `/tmp`), otherwise the Files app would show an empty `/home` and a private `/tmp`. Without the word the helper keeps the stricter view.
- Real systemd and a real host were not part of the automated tests (they use the real helper code on a throw-away directory and a fake link); see the CHANGELOG for what was tried by hand.

## Host to host

`copy` with a target on another connection: the server reads from the source host over SFTP and writes to the target host over SFTP **in a stream** (nothing is stored on the server). The file is first written under a temporary name `.julos-<random>.part` in the target folder (created new, never overwritten), checked for the expected size, then renamed (`posix-rename`, which replaces atomically on OpenSSH; otherwise the old file is deleted first). A failure, a cancel or a lost connection removes the temporary file; what was already finished stays. A **move** between hosts copies first and deletes at the source only what arrived safely, so a link that was skipped (and its folder) stays. Both hosts need an open session (open the target in the target chooser; a password-less connection asks there).

## Limits and honest edges

- Copy does not keep permissions, owner or modification time; links and special files are skipped (and counted in the result).
- Rename onto an existing file uses `posix-rename`; a server without it falls back to delete and rename (not atomic). Existence checks before a write are not atomic either; they are a courtesy, the server of the host stays the judge.
- A text file larger than 1 MiB shows its beginning and is not editable. Text up to 1 MiB opens in the simple editor ([FILES-EXPLORER.md](FILES-EXPLORER.md#4-editor)); saving is the confirmed upload of the whole file (`prepare upload`, then `remote/upload` with the token, overwrite shown in the sheet), so the editor adds no endpoint and no new right.
- The target path of a link is not shown (no `readlink` in the SFTP library).
- Listing a directory with more than 2000 entries shows the first 2000.

## Not built, and decisions

- **Root access** is built as its own place (see above), also with the editor (reading and saving go through the usual root confirmations). Not built there: permissions and owner changes, symbolic links, a view of the target of a link.
- **Key authentication** for the files is not offered; the logins hold passwords. Decision: use the same credentials as the terminal (the host login), add nothing new. Root is not a second stored login (see [HOSTS.md](HOSTS.md#login-one-user-and-password-per-host)).
- **Recycle bin, thumbnails, search on hosts** (the explorer filters the current folder by name), **a zip of a selection**: see [IDEAS.md](IDEAS.md). Sorting by name, date, type and size is built on the page (the server order of the list is only the default).
- Decision: the first host key must be confirmed (stricter than the terminal) because a file manager moves more data than a shell you watch.
- Decision: a typed password is held only for the one connection attempt; the pool keeps the authenticated session, never the password.
