- 2026-11-18 Picture engine for the Linux desktop (quality, latency, smoothness; research, nothing measured yet). Guacamole only sends PNG/JPEG/WebP tiles, no video; guacd decodes RDP GFX/H.264 and re-encodes it, and RDP has no quality parameter (only `force-lossless`). So it cannot become fluid. Candidates for a CPU-only KVM guest: **Selkies** (docs: attaches to an existing X.Org display, H.264 via WebCodecs over WebSocket, two-way clipboard with images, audio, file drag and drop, MPL-2.0, maintainers wanted), **Xpra** (HTML5 client with H.264/VP8 via WebCodecs, `xpra shadow` shows the whole screen, per-window apps need seamless mode, html5 client wants Xpra 7+ while Debian 13 packages are older), **KasmVNC** (starts its own X session, so no attach to an xrdp session; H.264/H.265/AV1 video mode since 1.5.0, GPL-2.0). No source gives CPU-only numbers, so measure on the real VM first: re-test GFX in guacd now that chansrv works, and prototype Selkies on display :10 from Android Chrome and a PC. Sources: github.com/selkies-project/selkies, docs.selkies.io, github.com/kasmtech/KasmVNC, xpra-org.github.io/xpra, guacamole.apache.org/doc/gug, github.com/neutrinolabs/xrdp/wiki/H.264-encoding. JulOS would then pick an engine per connection (guacd for RDP/SSH/Windows, a stream engine for the Linux desktop) behind the same login.
- 2026-11-18 Measured: Guacamole against Selkies on the Docker test desktop (Debian 13, xrdp 0.10, XFCE, 6 shared CPUs, no GPU, 940x520, Chromium in the app pane, one run each, so a first indication and not a benchmark). Load = a 640x360 30 fps test video (ffplay testsrc2) playing in the session; probe = a small square that toggles on a click, time from click to the colour change in the browser. Visible updates per second / click latency median, p90:
  - Guacamole, GFX off (today): 2.3 fps, 328 ms, 1272 ms (earlier run on a smaller screen 4.5 fps, 277 ms).
  - Guacamole, GFX on (`JULOS_RDP_GFX=on`): 2.7 fps, 619 ms, 2777 ms. GFX changes nothing important; the default stays off.
  - Selkies 2.2.1, WebSocket, software H.264, attached to display :10: 11.1 fps, 154 ms, 288 ms.
  - Idle (no video), click latency median: Guacamole 34 ms (p90 50), Selkies 70 ms (p90 181); the Guacamole number has no browser input path in it, so it is slightly optimistic.
  Not measured yet: text sharpness (H.264 against PNG/JPEG tiles), Android Chrome, the real VM (RAM and CPU while encoding), HTTPS (WebCodecs needs a secure context, so Selkies needs TLS or localhost). Measuring tools: `JULOS_RDP_GFX` switch in `GuacSpec`, `kB insgesamt` in the "Bildaufbau" log line.

- 2026-11-18 **Clean comparison (supersedes the earlier "Measured" entries above, those ran while other test jobs kept the machine at load 10-30 and used a coarse frame counter).** Same target (Docker test desktop, Debian 13, xrdp 0.10, XFCE), machine quiet (load 3-6 including the measuring browser), a 640x360 30 fps test video, real mouse clicks, frame rate counted from the video's own frame counter digits, one round each, 8-10 clicks, no GPU, Chromium in the app pane, loopback only:
  | Engine | frames shown per s (source 30) | click latency, video playing: median / p90 | click latency, idle: median / p90 |
  | Selkies 2.2.1 (software H.264, WebSocket, attached to the display) | ~31 | 53 / 87 ms | 28 / 41 ms |
  | the third engine (own C# RDP engine, OpenH264, WebCodecs; 1366x596) | 25 | 41 / 64 ms | 21 / 28 ms |
  | Guacamole through JulOS (1364x668) | 23 | 130 / 191 ms | 22 / 35 ms |
  Result: idle (typing, clicking) all three are equal at about 20-28 ms. With motion Guacamole is clearly worse in latency (about 3x) and shows 23 of 30 frames, Selkies shows all 30, the third engine 25. The earlier "2-5 fps" for Guacamole was an artefact of the loaded machine and the coarse counter. Not measured: text sharpness (H.264 against PNG/JPEG tiles), Android Chrome, a WAN link, the real VM, several rounds. the third engine was tested as a separate throw-away instance in the same Docker network; its sign-in for the target was an empty password of the throw-away test user (set and removed again), nothing real was touched.
- 2026-11-18 **Own stream engine against Guacamole, measured in the browser.** Docker test desktop (xrdp, XFCE), picture 1172x392, a 480x270 30 fps test video as load, click on a probe square until its colour changes on the display canvas (read with getImageData, 15 clicks per engine, one round each), machine quiet (load 4-6 including the measuring browser), loopback only, Chromium in the app pane. Stream engine: click latency median 81 ms (p90 98 ms), Guacamole: 154 ms (p90 247 ms). Server CPU during the run: stream engine about 16 % of one core (the JulOS container), Guacamole about 58 % (JulOS plus guacd about 47 %). The frame-rate column of this probe is not usable (the sampling loop itself is capped near 11 per second for both engines); the decoder in the browser produced about 23 pictures a second with the stream engine on a loaded machine. Under heavy machine load (load 15 for the stream run, 40-56 for the Guacamole run, so not comparable) the stream engine still answered in 79 ms while Guacamole needed 1.7 s and lost clicks. Found on the way: with the early version the stream stopped for good after a few hundred pictures (the window of unacknowledged pictures stayed full, not even a key frame request got an answer); the cause is not found, a watchdog now resets the window after 2 s and logs the state (commit 3385c50). Still not measured: text sharpness, Android Chrome, a WAN link, the real VM, several rounds.
- 2026-11-18 **A third engine with its own RDP client, read from its source (MIT, v0.23, read-only study).** A complete RDP client in C#, no guacd and no FreeRDP: NLA/CredSSP/NTLM (own MD4 and RC4, .NET crypto for the rest), legacy bitmap path (interleaved RLE, planar), drawing orders, channels (clipboard incl. files, RDPDR drive, sound, display control for resize, dynamic channels), about 11k lines, with unit tests and a FreeRDP cross check. No RemoteFX/RDPGFX from the server. The remote picture is written into an I420 frame in native memory (only the changed rectangles), encoded with libopenh264 (distribution package, BSD, about 1 MB) under its own rate controller (quantiser chosen from a bit-rate bucket, block-average "mosaic" as last resort; quick pictures while things move, the same picture re-encoded until sharp once the screen stands still), paced by the browser (at most 3 pictures in flight, each acknowledged after decoding) and decoded in the browser with WebCodecs (`avc1` taken from the stream's SPS). The engine folders `Display/Rdp` and `Display/Video` use only their own namespaces (the test projects link them by file glob), so they are separable; `ScreenSession` also needs the third engine's screen protocol and the browser page (about 2.3k lines). CPU in the three-way test, engine process only: the third engine about 14 %, guacd about 53 %, Selkies about +35 % on the target side (single samples). Risks: young and single-maintainer (3 stars, the engine moved into the third engine on 2026-11-16), hand-written NLA/NTLM, no server-side H.264, software encoding only, WebCodecs needs HTTPS. Open: text sharpness, Android, a real Windows host, a real xrdp VM.
